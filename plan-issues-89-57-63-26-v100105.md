# Issue #89 — «Скачивание EXE на Линукс»

## Факты (проверено)

- Реальные ассеты релиза `v1.0.1.5` (GitHub API, `releases/latest`): **`Workspace1C-linux-x64`** (53 277 027 байт) и **`Workspace1C.exe`** (84 934 435 байт). Никаких `.tar.gz`/`.AppImage`.
- Логика [`GitHubReleaseService.FindAsset`](Workspace1C/Services/GitHubReleaseService.cs:305) в Linux-ветке (`#else`, [IsPlatformAsset](Workspace1C/Services/GitHubReleaseService.cs:392)) **корректна для этих ассетов**: проход 1 — точное имя `Workspace1C-linux-x64`, проход 2 — `Contains("linux-x64")`, при этом любые `.exe` и `.zip` исключены. Символ `WINDOWS` в Linux-сборке не определён ([Workspace1C.csproj](Workspace1C/Workspace1C.csproj:40) — TFM `net10.0` + `LINUX`; тесты с `-p:BuildLinux=true` прокидывают `LINUX` отдельно).
- Следовательно **на стороне выбора ассета дефект не воспроизводится** в коде 1.0.1.4/1.0.1.5. Наиболее вероятные объяснения скриншота пользователя:
  1. Пользователь ещё на версии **≤ 1.0.1.3**, где Linux-ветка выбирала `.exe`: старое приложение скачивает Windows-EXE → обновление падает → исправленная версия к нему никогда не доезжает («застрявшие» пользователи).
  2. Отсутствие валидации скачанного файла: если по любой причине (старый код, сбой, подмена) скачался `.exe`, загрузчик пытается исполнить его на Linux, и обновление «не может завершиться» без понятной диагностики.

## Решение

### 89.1. Валидация скачанного бинарника перед применением (главная правка)

**Файлы:**
- [`Workspace1C/Services/UpdateService.Avalonia.cs`](Workspace1C/Services/UpdateService.Avalonia.cs) — метод `DownloadNewBinaryAsync` (вызывается в 3 местах: строки ~616, ~759) — Linux-путь.
- [`Workspace1C/Services/UpdateService.cs`](Workspace1C/Services/UpdateService.cs) — метод `DownloadAsync` (~строка 786) — Windows-путь, для симметрии.
- Логика валидации — как чистый статический хелпер рядом с [`UpdatePayload.cs`](Workspace1C/Services/UpdatePayload.cs) (например, `UpdatePayload.ValidatePlatformMagic(string filePath, bool linux)`), чтобы покрыть юнит-тестами без ФС.

**Правка:**
- Проверка первых байт файла: Linux — `\x7fELF` (ELF-магия), Windows — `MZ` (PE). Размер файла дополнительно сверяется с `release.AssetSize` (если > 0).
- При несовпадении: удалить/переменовать скачанный файл (`*.wrong-platform`), показать пользователю понятную ошибку: «Скачан файл для другой операционной системы. Обновление отменено. Скачайте сборку вручную: <HtmlUrl>», записать в лог URL и первые байты.
- Это гарантирует, что «застрявший» пользователь на любой старой версии больше не получит тихо сломанное обновление, а увидит инструкцию по ручной установке.

### 89.2. Диагностика выбора ассета

- В [`GitHubReleaseService.FindAsset`](Workspace1C/Services/GitHubReleaseService.cs:305) добавить (необязательный, через существующий `Log`) журнал выбранного имени ассета и URL. Логировать только результат (имя ассета), без спама.
- Матчинг по RID-суффиксу: текущий проход 1 (точное имя `AssetName`) фактически уже эквивалентен match по суффиксу `linux-x64`/`win-x64`, т.к. `AssetName` = `Workspace1C-linux-x64`/`Workspace1C.exe`. Менять **не нужно** — только зафиксировать тестом.

### 89.3. Ответ в issue

- Запросить у 7OH точную версию приложения со скриншота (если < 1.0.1.4 — это подтверждает гипотезу «застрявшей» версии; порекомендовать ручную установку `Workspace1C-linux-x64` из релиза 1.0.1.5).

## Юнит-тесты ([`Workspace1C.Tests/GitHubReleaseServiceTests.cs`](Workspace1C.Tests/GitHubReleaseServiceTests.cs))

1. **Реальный список ассетов v1.0.1.5** (оба ассета с настоящими именами/URL/size): `FindAsset` на Linux-ветке должен вернуть `…/download/v1.0.1.5/Workspace1C-linux-x64` и `size=53277027`; на Windows-ветке — `Workspace1C.exe` и `size=84934435`. Тест платформозависимый — использовать существующие в файле приёмы условной компиляции (`#if LINUX` / `#if WINDOWS`, см. комментарии в csproj тестов).
2. Новый тест хелпера валидации: файл с `\x7fELF` → валиден на Linux, невалиден на Windows; `MZ` → наоборот; короткий/пустой файл → невалиден; size-сверка при `AssetSize>0`.
3. Обратный кейс: список, где Linux-ассет назван `Workspace1C` (старое имя) — сохраняется поведение `IsPlatformAsset`.

## Риски

- Низкие: валидация может отклонить файл, если GitHub изменит формат доставки (сейчас — сырой single-file ELF, риск минимален). Не ломать существующий сценарий, когда `AssetSize == 0` (не сверять размер).

# Issue #57 — «Общая авторизация»: не подставляется + сквозной аудит пароля

## Причина (анализ кода)

Цепочка: статические поля [`OneCLauncher.CommonEnterpriseAuthorization` / `CommonConfiguratorAuthorization` / `CommonAuthorization`](Workspace1C/Services/OneCLauncher.Arguments.Shared.cs:26) наполняются из настроек в [`MainViewModel`](Workspace1C/ViewModels/MainViewModel.cs:508) (старт) и сохраняются корректно ([`MainViewModel.Launch.cs`](Workspace1C/ViewModels/MainViewModel.Launch.cs:701), [`SettingsWindow.xaml.cs`](Workspace1C/Views/SettingsWindow.xaml.cs:825) — `AuthenticationMode` выставляется явно, `IsDefault` [определяется как](Workspace1C/Models/InfobaseAuthSettings.cs:37) `Prompt && пустые User/Password`).

Ключевой дефект — **шаг 2 резолвера** [`InfobaseAuthResolver.Resolve`](Workspace1C/Services/InfobaseAuthResolver.cs:100): авторизация базы `Connection` считается «заданной», если `AuthenticationMode != Prompt` **ИЛИ** заполнен user/пароль. Сценарий пользователя: «у базы выключена насильная авторизация» → у базы фактически режим **`Windows` (авторизация ОС)** — шаг 2 возвращает его, и **общая авторизация (шаг 3) не применяется никогда**. Платформа получает `/WA+` без `/N`/`/P` → «не подставляет ничего».

## Решение

### 57.1. Правка семантики приоритета в `InfobaseAuthResolver`

**Файл:** [`Workspace1C/Services/InfobaseAuthResolver.cs`](Workspace1C/Services/InfobaseAuthResolver.cs) — метод `Resolve` (перегрузка с 3 общими, строка 74; одиночная — строка 44 — просто делегирует).

**Новые правила (сохраняя приоритет собственной авторизации режима):**
1. `EnterpriseAuth`/`ConfiguratorAuth` — как сейчас (не `IsDefault` → используется).
2. `Connection` считается «заданной» и перекрывает общую **только** если:
   - `AuthenticationMode == Credentials` **и** `User` непуст; **или**
   - `AuthenticationMode == Windows` **и** общая авторизация режима не является `Credentials` (т.е. нет явных общих учётных данных, которые обязаны подставиться).
3. Иначе — шаг 3 (общая по режиму → legacy → Prompt).

Реализация: перед шагом 2 вычислить эффективную общую для режима (`modeCommon`) и в условии шага 2 добавить проверку `!(conn.AuthenticationMode == AuthenticationMode.Windows && modeCommon is { } m && !m.IsDefault && m.AuthenticationMode == AuthenticationMode.Credentials)`. Вычисление `modeCommon` перенести выше шага 2 (без изменения результата шага 3).

### 57.2. Сквозной аудит мест использования пароля (требование 7OH)

Единая точка — `InfobaseAuthResolver`. Аудит по результатам поиска по решению (паттерны `Usr=`, `/P"`, `.Password`, `Pwd=`):

# Issue #63 — «Доработка публикации баз»: конфиги Apache-служб

## Причина (подтверждено кодом)

[`ApacheInstanceDetector.Windows.DetectWindows`](Workspace1C/Services/ApacheInstanceDetector.Windows.cs:21) читает из реестра только `ImagePath`. У служб, созданных обёрткой 1С/Apache monitor, ключи `-d`/`-f` в `ImagePath` **отсутствуют** (`"c:\Apache\Apache24\bin\httpd.exe" -k runservice`) — они лежат в подразделе параметров службы:

```
HKLM\SYSTEM\CurrentControlSet\Services\<служба>\Parameters\ConfigArgs  (REG_MULTI_SZ)
  →  [ "-d", "c:\Apache\Apache24", "-f", "conf\httpd27.conf" ]
```

Поэтому все службы сводятся к дефолтному `httpd.conf` — что и видно в логе пользователя. Обе предыдущие правки (синтетический инстанс из конфига в 1.0.1.2, извлечение `-d`/`-f` из `ImagePath` + устойчивая токенизация в 1.0.1.4) не помогали, потому что данные просто не в `ImagePath`.

## Решение

**Файлы:**
- [`Workspace1C/Services/ApacheInstanceDetector.Windows.cs`](Workspace1C/Services/ApacheInstanceDetector.Windows.cs) — `DetectWindows` (строки 21-65).
- [`Workspace1C/Services/ApacheInstanceDetector.cs`](Workspace1C/Services/ApacheInstanceDetector.cs) — [`ParseWindowsServiceImagePath`](Workspace1C/Services/ApacheInstanceDetector.cs:50) (чистая функция, покрыта тестами).

**Правки:**

1. В `DetectWindows`, для каждой службы, после чтения `ImagePath`:
   ```csharp
   var configArgs = ReadConfigArgs(key); // new: key.OpenSubKey("Parameters")?.GetValue("ConfigArgs") as string[]
   ```
   Новая перегрузка чистой функции:
   ```csharp
   public static ApacheInstance? ParseWindowsServiceImagePath(
       string serviceName, string displayName, string description,
       string? imagePath, string? configArgs)
   ```
   Внутри перегрузки: собрать полную командную строку `commandLine = imagePath + " " + string.Join(" ", configArgs)` (когда `configArgs` непуст) и передать в существующую логику — парсер `ExtractSwitch`/`Tokenize` уже умеет `-d`/`-f` с кавычками и без. Старая 4-аргументная перегрузка делегирует в новую с `configArgs = null` (обратная совместимость для тестов/вызовов).
2. Относительный `-f conf\httpd27.conf` уже резолвится от ServerRoot в существующем коде ([строки 70-77](Workspace1C/Services/ApacheInstanceDetector.cs:70)) — сохранить.
3. `RawCommandLine` для лога CM_PUBLISH: если `ConfigArgs` непуст, записывать `ImagePath="…"; ConfigArgs=-d c:\Apache\Apache24 -f conf\httpd27.conf` — пользователь сразу увидит в логе источник параметров (требование видимости данных службы). Лог `CM_PUBLISH` в [`WebPublishViewModel.cs`](Workspace1C/ViewModels/WebPublishViewModel.cs) дописывать не нужно — он печатает `RawCommandLine` как есть.
4. `ReadConfigArgs`: устойчиво к отсутствию подраздела `Parameters`/значения (`null` → прежнее поведение); элемент массива может быть одной строкой `"-d c:\Apache\Apache24 -f conf\httpd27.conf"` (вариант из ранних комментариев 7OH) — склейка через пробел покрывает оба формата.

## Юнит-тесты ([`ApacheInstanceDetectorTests.cs`](Workspace1C.Tests/ApacheInstanceDetectorTests.cs))

Новые кейсы 5-аргументной перегрузки (чистые, без реестра):
1. `imagePath = "\"c:\\Apache\\Apache24\\bin\\httpd.exe\" -k runservice"`, `configArgs = "-d c:\\Apache\\Apache24 -f conf\\httpd27.conf"` (как строка) → `ServerRoot=c:\Apache\Apache24`, `ConfPath=c:\Apache\Apache24\conf\httpd27.conf`.
2. То же в формате REG_MULTI_SZ-массива `"-d", "c:\Apache\Apache24", "-f", "conf\httpd27.conf"` (join-имитация) → тот же результат.
3. `configArgs = null` / пустой → поведение идентично прежнему (регресс).
4. `configArgs` с незакрытой кавычкой в `imagePath` → токенизация-фолбэк по-прежнему извлекает `-d`/`-f`.
5. Конфликт: `-d` есть и в `ImagePath`, и в `ConfigArgs` → приоритет `ConfigArgs` (документировать в комментарии).

## Риски

- Низкие: служба с посторонним `ConfigArgs` (не Apache-формат) — парсер просто не найдёт `-d`/`-f` и останется прежнее поведение. Сборка Windows-only (`#if WINDOWS`) — Linux-сборка не затронута; тесты чистой функции кроссплатформенные.

## п.4 — белая подсветка кнопок неактивного главного окна

**Причина (анализ цепочки):**
- Механизм введён в 1.0.1.4: стиль [`WindowControlButton`](Workspace1C/App.xaml:161) использует `HoverBrush = {DynamicResource WindowButtonInactiveHoverBrush}`; [`ThemeManager.ApplyWindowButtonStyle`](Workspace1C/Themes/ThemeManager.cs:203) ставит ресурс: тёмная тема → `#334155` ([`InactiveHoverHex`](Workspace1C/Themes/ThemeFeatureMap.cs:153)), светлая → «дневная» подложка стиля.
- Дыра 1 — **исключение MacOS/Glass**: [`InactiveHoverHex`](Workspace1C/Themes/ThemeFeatureMap.cs:155) для стилей кнопок `MacOS` и `Glass` всегда возвращает светлую подложку (`ButtonMetrics(style, dark: false).HoverHex`). Если у пользователя стиль кнопок окна Glass — подсветка неактивного окна по-прежнему полупрозрачно-белая.
- Дыра 2 — **Avalonia**: [`WindowButtonThemeMetrics.Avalonia.cs:53`](Workspace1C/Themes/WindowButtonThemeMetrics.Avalonia.cs:53) вычисляет `InactiveHover` с зашитым `dark: false` → Avalonia-кнопки, читающие метрики (не ресурс), всегда получают светлую неактивную подложку.
- Дыра 3 (проверить): порядок применения темы — `ApplyWindowButtonStyle` должен вызываться при **каждом** применении полной темы/схемы ([`ThemeManager.cs:189`](Workspace1C/Themes/ThemeManager.cs:189) `ApplyScheme`-путь), иначе ресурс остаётся от прошлой темы.

**Правки:**
1. [`ThemeFeatureMap.InactiveHoverHex`](Workspace1C/Themes/ThemeFeatureMap.cs:153): убрать исключение `Glass` (тёмная неактивная подложка и для Glass); для `MacOS` оставить цветной «светофор» (круги всегда цветные — это не «белая подсветка»), но явно проверить скрином.
2. [`WindowButtonThemeMetrics.Avalonia.cs`](Workspace1C/Themes/WindowButtonThemeMetrics.Avalonia.cs:53): передавать фактический `dark` (из `ThemeManager.CurrentTheme == DarkThemeName` или `CurrentFullTheme.IsDark`), а не `false`.
3. Убедиться, что `ApplyWindowButtonStyle()` вызывается из всех путей смены темы (WPF `ThemeManager.ApplyTheme`/`ApplyScheme`/полная тема; Avalonia-аналог [`ThemeManager.Avalonia.cs:188`](Workspace1C/Themes/ThemeManager.Avalonia.cs:188)) — при необходимости добавить вызов.
4. WPF-триггер активности: [`UpdateTitleBarAppearance`](Workspace1C/Views/MainWindow.xaml.cs:1112) переключает стили `onAccent: active` — подтверждить, что при `active=false` действительно применяется базовый `WindowControlButton` (не OnAccent-вариант с белым hover) для всех трёх кнопок, включая Close (`WindowControlCloseButton`).

**Тесты:**
- Новый тест в существующем файле тем (`ThemeFormLabelTests.cs` или отдельный `Issue26WindowButtonTests.cs`): `InactiveHoverHex(Fluent/Minimal/Classic, dark: true) == "#334155"`, `InactiveHoverHex(Glass, dark: true) == "#334155"`; `InactiveHoverHex(style, dark: false)` — прежние значения (регресс).
- Тест `WindowButtonThemeMetrics` (Avalonia): `InactiveHover` при `dark: true` — тёмный hex.
- Тест ресурса: после применения тёмной темы `app.Resources[WindowButtonInactiveHoverBrushKey]` — `#334155` (по образцу существующих тестов ThemeManager, если есть).
