## 2. Issue #89 — «Скачивание EXE на Линукс» (автообновление, «Call from invalid thread»)

### Симптом (7OH, 2026-11-02 07:42)
Ассет выбирается верно (`Workspace1C-linux-x64`, 53365802 байт), загрузка доходит
до конца (все байты скачаны), затем: `InvalidOperationException: Call from invalid
thread; dest=/tmp/cm-update-…/Workspace1C.v1.0.1.21.new; скачано байт=53365802`.
После ошибки **файлы исчезают** — проверить скачанное нельзя.

### Корневая причина (по анализу кода)
1. [`BackgroundDownloadManager.Complete(id)`](Workspace1C/Services/BackgroundDownloadManager.cs:253)
   синхронно вызывает `RaiseChanged()`/`Completed?.Invoke` **из потока загрузки**.
2. Подписчик главного окна: [`MainViewModel.Downloads.cs:164-169`](Workspace1C/ViewModels/MainViewModel.Downloads.cs:164) —
   `OnBackgroundDownloadsChanged` → `RefreshDownloadsIndicator()` пишет observable-свойства
   VM (`HasActiveDownloads`, `DownloadsStatusText`, `ActiveDownloadsProgress`, `DownloadsEtaText`)
   **без маршалинга в UI-поток**. WPF прощает (авто-маршалинг биндингов), Avalonia
   бросает `InvalidOperationException: Call from invalid thread` при применении
   значения к контролу.
3. Исключение возникает внутри [`DownloadNewBinaryAsync`](Workspace1C/Services/UpdateService.Avalonia.cs:884)
   (прогресс-колбэк → `ReportProgress` → `Changed`; и/или финальный
   `BackgroundDownloadManager.Complete` на строке 989) → ловится `catch` на строке 992,
   который **удаляет `dest` и `.etag`** (строки 1000–1001) — отсюда «файлы исчезают».
   На Windows тот же код работает, поэтому воспроизводится только на Linux.

### Изменения
1. **Маршалинг подписки** ([`MainViewModel.Downloads.cs`](Workspace1C/ViewModels/MainViewModel.Downloads.cs:168)):
   `OnBackgroundDownloadsChanged` → через `UiDispatch` / `Dispatcher.UIThread.Post`
   (по образцу остальных мест; проверить, как другие платформенные подписчики
   используют [`UiDispatch.cs`](Workspace1C/Services/UiDispatch.cs)).
2. **Аудит остальных подписчиков** `BackgroundDownloadManager.Changed/Completed/Failed`
   (окно скачивания платформы, цепочки обновлений, индикатор Avalonia) — все должны
   маршалить; оформить это правилом в XML-доке менеджера («события из фонового потока,
   подписчики обязаны маршалить» — комментарий уже есть, проверить соблюдение).
3. **Диагностика/карантин**: при неизвестной ошибке загрузки не удалять `dest`
   молча — переименовать в `*.download-error` (по образцу карантинного
   `*.wrong-platform` из [`UpdatePayload`](Workspace1C/Services/UpdatePayload.cs)) и писать
   в журнал `CM_UPDATES`. Тогда у пользователя останется файл для проверки (просьба 7OH).
4. Проверить, что «тихий» catch в [`DownloadNewBinaryAsync`](Workspace1C/Services/UpdateService.Avalonia.cs:992)
   не глотает стек: добавить `ex.ToString()` (или хотя бы StackTrace верхнего кадра) в журнал.

### Тесты (Workspace1C.Tests)
- [`Issue89PlatformValidationTests.cs`](Workspace1C.Tests/Issue89PlatformValidationTests.cs) — дополнить:
  тест, что `RefreshDownloadsIndicator` вызывается через абстракцию диспетчера
  (инжектируемый `UiDispatch`), а не напрямую из потока события;
- тест карантинного переименования `*.download-error` при ошибке загрузки
  (по образцу тестов `RejectWrongPlatformFile`).

### Риски
- Низкие. Важно не сделать двойной Post (двойное обновление индикатора безвредно).

## 3. Issue #92 — «Выгрузка списка баз в файл *.dt» (массовая выгрузка не работает)

### Симптом (7OH, 2026-11-02 07:50, ZIP `diagnostics_20261102_104926.zip`)
После v1.0.1.21 ошибки по базам **пропускаются** (фикс fail-fast работает),
но **выгрузки не происходит ни по одной базе**.

### Корневая причина — выяснить по диагностике ZIP (шаг 1)
В v1.0.1.21 добавлены журнальные строки «запущен ibcmd (PID …)» и детали
автоподстановки СУБД ([`IbcmdService.ProcessStarted`](Workspace1C/Services/IbcmdService.cs),
[`ClusterInfobaseCredentialsResolver.cs`](Workspace1C/Services/ClusterInfobaseCredentialsResolver.cs)) —
ZIP должен показать, на чём именно ломается прогон. Кандидаты по коду:

1. **Автоподстановка СУБД не даёт профиля**: rac 8.5.4 отдаёт пустой тип СУБД /
   имя ИБ в кластере не совпадает с именем базы приложения («Demo 27» vs
   «Demo_8.3.27» — видно в логах #79 от 2026-11-01 16:04) → `ResolveAsync` возвращает
   null → операция фиксирует ошибку и `continue` → все базы «пропущены с ошибкой».
2. **Неверные аргументы ibcmd** после рефакторинга v1.0.1.21 (`--dbms=…` из профиля
   резолва), либо ibcmd стартует и мгновенно падает — код выхода/текст должен быть в ZIP.
3. Регрессия в [`BatchOperationsViewModel.RunAsync`](Workspace1C/ViewModels/BatchOperationsViewModel.cs)
   (правка v1.0.1.21: `return`→`continue`, `IsRunning` в `try/finally`) — проверить,
   что при успешном пути прогресс и запуск dump действительно выполняются.

### Изменения (после разбора ZIP — уточнить)
1. Скачать и разобрать `https://github.com/user-attachments/files/34261345/diagnostics_20261102_104926.zip`
   (логи приложения + журнал окна). 
2. Точечный фикс найденной причины (ожидаемо: сопоставление имён баз в rac —
   матчинг по имени ИБ кластера нормализовать (без учёта регистра/подчерков) или
   матчинг по `Ref`/серверу; и/или при пустом типе СУБД честный fail с понятной
   ошибкой по каждой базе, а не «пропуск»).
3. Гарантировать, что «пропуск с ошибкой» всегда даёт **видимую причину по каждой
   базе** в журнале окна (сейчас формулировки вида «операция завершилась ошибкой (1 сек)»
   без текста).

### Тесты
- [`Issue92BatchDumpTests.cs`](Workspace1C.Tests/Issue92BatchDumpTests.cs) — дополнить:
  нормализация сопоставления имён ИБ в `ClusterInfobaseCredentialsResolver`;
  в журнале по каждой ошибке присутствует текст причины.

### Риски

## 4. Issue #79 — «Развернуть тестовую копию»: после ОК ничего не происходит

### Симптом (7OH, 2026-11-02 07:46, ZIP `diagnostics_20261102_081427.zip`)
Сервер доступен, **в логах тихо**, после ОК «НИ ЧЕ ГО» (скрин 605×300 — по-видимому,
диалог/окно мастера с кнопкой ОК).

### Корневая причина — выяснить по ZIP + коду (шаг 1). Гипотезы по коду:
1. **Молчаливый abort pre-валидации** (v1.0.1.21): [`TestDeployService.DeployAsync`](Workspace1C/Services/TestDeployService.cs:83-95)
   — если `DumpEngine == Ibcmd` и база клиент-серверная, вызывается
   [`ResolveSourceDumpProfileAsync`](Workspace1C/Services/TestDeployService.cs:434):
   сохранённого профиля нет → rac-резолв не находит базу (имя в кластере
   «Demo_8.3.27» ≠ имя в приложении «Demo 27», см. лог 2026-11-01 16:04) →
   поля формы не считаются «описывающими источник»
   ([`TestDeployPlanner.FormFieldsDescribeSource`](Workspace1C/Services/TestDeployPlanner.cs)) →
   возвращается `(null, TestDeploy.DbmsProfileNotFound)` и сценарий завершается
   **до шага «Выгрузка»**. Если окно мастера в этом состоянии показывает лишь
   диалог с ОК (или ничего), пользователь видит «ничего не происходит».
2. **Резолв не журналируется в журнал приложения**: `log?.Invoke(...)` пишет только
   в журнал мастера; в app-лог (`CM_RAC`) пробы rac попадают лишь при вызовах rac —
   при раннем выходе «в логах тихо».
3. Проверить обработчик ОК в окне ([`TestDeployWindow.cs`](Workspace1C/Views/TestDeployWindow.cs),
   [`TestDeployWindow.Avalonia.cs`](Workspace1C/Views/TestDeployWindow.Avalonia.cs)):
   не блокируется ли команда/не проглатывается ли `result.ErrorMessage` при
   раннем возврате (возврат до `result.Steps` → пустой журнал).

### Изменения
1. Разобрать ZIP `diagnostics_20261102_081427.zip` (подтвердить, на чём прерывается).
2. **Резолв источника всегда журналируется** (Log, категория CM_TESTDEPLOY/CM_RAC):
   «профиль: есть/нет», «rac: пробуем/найдено/не найдено (по каким именам искали)»,
   «поля формы: считаем/не считаем данными источника и почему».
3. **Понятное сообщение вместо «ничего»**: при `profileError` окно мастера обязано
   показать ошибку в журнале окна + диалог с текстом «чего не хватает» (профиль СУБД
   кнопкой «Профиль СУБД для ibcmd…» / данные rac) — не просто закрытие/молчание.
4. **Сопоставление имён rac** (общее с #92): нормализовать матчинг имени ИБ кластера
   (регистр/подчерки/пробелы) или матчить по серверу+Ref; после фикса выгрузка
   источника должна проходить по rac-данным без ручного профиля.
5. Если ZIP покажет иной сценарий (например, диалог подтверждения с ОК, после
   которого команда не стартует) — точечный фикс по факту.

### Тесты
- [`Issue79TestDeployWindowTests.cs`](Workspace1C.Tests/Issue79TestDeployWindowTests.cs),
  [`TestDeployTests.cs`](Workspace1C.Tests/TestDeployTests.cs) — дополнить:
  матчинг имён rac (нормализация), журналирование шагов резолва, показ ошибки
  pre-валидации в UI-модели мастера.

### Риски
- Средние: каскад с #92 (общий резолвер). Изменение матчинга имён не должно
  подставлять чужую базу.

## 5. Issue #83 — «Информация о лицензиях в Серверы 1С» (каракули + таблица)

### Корневая причина (по анализу кода)
- [`ProcessRunner.RunAsync`](Workspace1C/Services/ProcessRunner.cs:87) читает
  stdout/stderr как **UTF-8 по умолчанию** (`outputEncoding ?? Encoding.UTF8`).
  Правильная кодировка существует ([`ConsoleOutputEncoding()`](Workspace1C/Services/ProcessRunner.cs:56),
  cp866 на русской Windows), но **каждый вызывающий обязан передать её явно** —
  а [`RingLicenseService.RunProcessAsync`](Workspace1C/Services/RingLicenseService.cs:336-337)
  её не передаёт → «каракули».
- «Каракули» ломают заголовки таблицы → [`RingLicenseParser.Parse`](Workspace1C/Services/RingLicenseService.cs:86)
  не распознаёт `IsLikelyLicenseHeader` → срабатывает запасной free-form разбор →
  на вкладке «Лицензии» виден сырой список вместо таблицы (второй вопрос 7OH:
  «как этот список превратится в таблицу с колонками»).
- Пользователь просит: **сделать фикс кодировки правилом для ВСЕХ мест работы
  с консольным выводом**.

### Изменения
1. **Центральное правило декодирования** в [`ProcessRunner.cs`](Workspace1C/Services/ProcessRunner.cs):
   - вариант A (рекомендуется): `RunAsync` читает **сырые байты** и декодирует
     эвристикой «UTF-8 → cp866 → cp1251» по числу U+FFFD — по образцу
     `RacClient.DecodeRacOutput` (см. [`RacClient.cs:1234`](Workspace1C/Services/RacClient.cs:1234));
     вынести декодер в общий хелпер (например, `ConsoleOutputDecoder`) и
     переиспользовать в `RacClient`;
   - вариант B (минимальный): по умолчанию `outputEncoding: null` → `ConsoleOutputEncoding()`
     (cp866 на Windows). Риск: утилиты, реально пишущие UTF-8, сломаются — поэтому A надёжнее.
2. **Аудит всех вызовов** `ProcessRunner.RunAsync`/`ProcessStartInfo` с чтением вывода
   (ring, webinst, ibcmd, Designer, git, pg_dump, sqlcmd, where/which) — убрать
   локальные opt-in кодировки там, где теперь работает общее правило; отдельно
   проверить [`DesignerCommandRunner.cs:180-183`](Workspace1C/Services/DesignerCommandRunner.cs:180)
   (cp1251 — файловые артефакты, не консоль: оставить как есть).
3. **`RingLicenseService`** — после центрального фикса проверить на реальном выводе
   (из логов CM_RAC пользователя — там есть сырой ответ ring) что
   `RingLicenseParser` строит таблицу; при необходимости дополнить
   `IsLikelyLicenseHeader`/`SplitCells` под фактический формат ring 0.20.
4. Вкладка «Лицензии» ([`ServerMonitorWindow.xaml`](Workspace1C/Views/ServerMonitorWindow.xaml) +
   Avalonia): убедиться, что при успешно распознанной таблице показывается **таблица
   с колонками** (тип, серийник, версия, модуль, пользователь, срок), а сырой текст —
   только при нераспознанном ответе.

### Тесты
- [`Issue83LicenseTabTests.cs`](Workspace1C.Tests/Issue83LicenseTabTests.cs),
  [`Issue83RingPathRegistryTests.cs`](Workspace1C.Tests/Issue83RingPathRegistryTests.cs) — дополнить:
  - `ConsoleOutputDecoder`: cp866-байты → русский текст; UTF-8-байты не ломаются;
  - `RingLicenseParser.Parse` на реальном (корректно декодированном) выводе ring
    из лога пользователя → заполненные колонки;
  - регресс: `ProcessRunResult` для cp866-вывода без явной кодировки.

### Риски
- Низкие-средние: эвристика декодирования затрагивает все консольные утилиты —
  гнать существующие тесты rac/webinst/ibcmd; пароль с кириллицей
  ([`StartManagerImporter.cs`](Workspace1C/Services/StartManagerImporter.cs)) —
  файловая cp1251, не трогать.

## 6. Issue #100 — «Линукс — пробел» в модальном диалоге

### Симптом (7OH, 2026-11-02 06:49)
На Windows пробел нажимает единственную кнопку диалога. На Linux диалог
«проверить обновления» (одна кнопка «ОК»): пробел **не** нажимает ОК, а
открывает меню перекрытого окна.

### Корневая причина — исследовать на этапе реализации. Кандидаты:
1. Диалог (вероятно [`MaterialMessageWindow.Avalonia.cs`](Workspace1C/Services/MaterialMessageWindow.Avalonia.cs))
   при открытии **не забирает фокус** / не устанавливает `Focus` на кнопку по умолчанию
   → клавиатура остаётся у владельца, Space трактуется его меню/акселератором.
2. Проверить путь показа «проверить обновления» (результат проверки → диалог с ОК):
   `ShowDialog` vs `Show` + владелец; в Avalonia модальность блокирует ввод
   родителя только при `ShowDialog` — если диалог показан иначе, ввод уходит в родителя.
3. Отсутствует обработка `KeyDown` (Space/Enter) на диалоговом базовом классе
   ([`EscClosableWindow.cs`](Workspace1C/Views/EscClosableWindow.cs) — только Esc?).

### Изменения
1. В Avalonia-версии диалога сообщений: при открытии — `ShowDialog<T>(owner)`,
   фокус на кнопку по умолчанию; обработчик `KeyDown`: `Space`/`Enter` → команда
   кнопки по умолчанию (проверить, что не задваивается при штатном фокусе).
2. Прогнать «трассировку модальных окон» (она уже попадает в ZIP диагностики,
   [`MenuCloseTrace`](Workspace1C/Services/MenuCloseTrace.cs)) — проверить, что
   диалог вообще зарегистрирован как модальный.
3. Проверить другие Avalonia-диалоги с одной кнопкой (результаты операций и т.п.) —
   fix на уровне общего окна сообщений закроет их разом.

### Тесты
- Юнит-тест на чистую логику (если вынести «какая кнопка реагирует на Space/Enter»);
  остальное — ручная проверка на Linux (и регресс на Windows/WPF: пробел работает).

### Риски
- Средние: нет постоянного Linux-стенда у разработчика → обязательна проверка
  7OH; предложить **prerelease-сборку** (workflow_dispatch с параметром prerelease
  в [`release.yml`](.github/workflows/release.yml) — уже существует с 1.0.1.8).
