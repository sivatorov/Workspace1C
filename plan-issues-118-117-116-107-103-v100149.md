## Issue #118 «Не найден метод "System.__ComObject.Count"» (RafaIS) — ПРИОРИТЕТ 1

### Разбор проблемы

Все операции с COM-коннектором идут через внешний процесс Windows PowerShell 5.1 ([`Services/ComScriptRunner.cs`](Workspace1C/Services/ComScriptRunner.cs)): члены объектов 1С вызываются через IDispatch-функции `G`/`S`/`M` из [`ComScriptRunner.Prelude`](Workspace1C/Services/ComScriptRunner.cs:73). Ошибка «Не найден метод "System.__ComObject.Count"» — это текст от 1С COM-объекта, который всплывает там, где скрипт безусловно вызывает `M $coll 'Count'` на коллекции:

- [`Services/InfobaseUsersService.cs:58-66`](Workspace1C/Services/InfobaseUsersService.cs:58) — операции `list`/`roles`: `$n=M $arr 'Count'` (пользователи), `$rn=M $rs 'Count'` (роли), `M $ur 'Contains' $r` (проверка роли пользователя);
- [`Services/ScheduledJobsService.cs:117-136`](Workspace1C/Services/ScheduledJobsService.cs:117) — операции `list`/`upsert`/`verify`: `$n=M $arr 'Count'`.

Причина падения (скриншот в issue): объект, на котором вызывается `Count`, оказывается не той коллекцией, которую ожидает скрипт (например, `Roles`/`InfoBaseUsers` вернул объект без члена `Count` — зависит от версии платформы/варианта коннектора V82/V83, либо промежуточный объект оказался `null`/другого типа). Любое исключение в `Invoke-Op` уходит в общий `catch` скрипта [`ComScriptRunner.Main`](Workspace1C/Services/ComScriptRunner.cs:83) с кодом `op` — пользователь видит сырую ошибку.

C#-сторона безопасна: [`ComReadHost.InvokeGet`](Workspace1C/Services/ComReadHost.cs:1369) уже обёрнут в try/catch.

### Изменения

1. [`ComScriptRunner.Prelude`](Workspace1C/Services/ComScriptRunner.cs:73) — добавить безопасные помощники:

   ```powershell
   # Число элементов коллекции 1С через IDispatch; -1 — член Count недоступен/объект не коллекция.
   function N($o,$n){try{if($null -eq $o -or $o -isnot [System.__ComObject]){return -1};return [int](M $o 'Count')}catch{return -1}}
   # Безопасный вызов метода с диагностикой: при отказе возвращает $null и пишет причину в $script:opErr.
   function Mt($o,$n){try{$script:opErr='';return (M $o $n @args)}catch{$script:opErr=(Err $_);return $null}}
   ```

   Имена (`N`, `Mt`) выбрать так, чтобы не конфликтовать с телами операций; при желании можно встречать их inline в телах. Существующие `G`/`S`/`M` не трогать (другие скрипты зависят).

2. [`InfobaseUsersService.cs`](Workspace1C/Services/InfobaseUsersService.cs:53) — тела `list`/`roles`:
   - `$n=M $arr 'Count'` → `$n=N $arr`; при `$n -lt 0` возвращать из `Invoke-Op` диагностику: `@{ok=$true; warn='nocount'; what='InfoBaseUsers/GetUsers'; err=$script:opErr}` или через JSON-поле `error` c понятным сообщением («объектная модель вернулаunexpected тип — проверьте версию платформы»), а не падение всего скрипта;
   - `$rn=M $rs 'Count'` и `$rs`/`$ur` — те же проверки; `M $ur 'Contains' $r` обернуть в try/catch (роль без `Contains` → считать «не содержит», а не падение);
   - `M $arr 'Get' $i` — только при `$n -gt $i` (после безопасного Count).

3. [`ScheduledJobsService.cs`](Workspace1C/Services/ScheduledJobsService.cs:116) — те же замены в `list`/`upsert`/`verify`.

4. Диагностика: в ответе скрипта при отказе добавлять класс объекта (например, попытка `$o.GetType().FullName` в try/catch) — чтобы в лог попадало «Count отсутствует у …». Вызывающие сервисы уже пишут `result.Error` в лог окна — диагностика дойдёт до пользователя без доп. правок UI.

### Тесты

- Юнит-тест на склейку скрипта (`BuildScript`) — что Prelude содержит `function N(` и тела операций используют `N $arr`/`N $rs` (строковая проверка, по аналогии с существующими тестами `ComScriptRunnerTests`, если есть).
- Регресс-тест `ParseOutput`: ответ с `warn`-полем не ломает разбор.

### Риски

- Минимальные: правки только PowerShell-тел; C#-контракт (`ComScriptResult`) не меняется, добавляется необязательное поле.
- Поведение на нормальных платформах не меняется: `N` возвращает то же, что и старый вызов.
- Требуется Windows-машина для ручной проверки (COM недоступен на Linux-сборке).

**Причина.** [`ExtensionsViewModel.CfePath`](Workspace1C/ViewModels/ExtensionsViewModel.cs:86): автоподстановка имени срабатывает **только если поле имени пустое** (`string.IsNullOrWhiteSpace(_extensionName)`). **Изменения:**

1. [`ExtensionsViewModel`](Workspace1C/ViewModels/ExtensionsViewModel.cs:19) — добавить флаг `_extensionNameEdited` (пользователь вручную правил имя). В сеттере `ExtensionName` ставить `true`, если значение отличается от автоподставленного; в сеттере `CfePath` — автоподставлять имя, если `!_extensionNameEdited`, при этом **перезаписывать** старое имя. Дополнительно: сбрасывать `_extensionNameEdited=false`, когда пользователь очистил поле имени вручную (пустое значение).
2. Проверить WPF-окно [`Views/ExtensionsWindow.cs`](Workspace1C/Views/ExtensionsWindow.cs) и Avalonia [`Views/ExtensionsWindow.Avalonia.cs`](Workspace1C/Views/ExtensionsWindow.Avalonia.cs): выбор файла должен идти через сеттер `CfePath` VM (не записывать напрямую в контрол); если путь устанавливается мимо VM — перенаправить.
3. [``ConfigExtensionService.SuggestName``](Workspace1C/Services/ConfigExtensionService.cs:57) не менять — он корректен; тесты на него дополнить кейсом «повторный выбор файла перезаписывает непользовательское имя» (тест VM: симуляция сеттеров).

## Issue #103 «Значки запуска в режиме Предприятия» — маркер отладки — ПРИОРИТЕТ 6

## Нереализуемые/спорные пункты и готовые формулировки комментариев

### #117 п.1 — флажки «Безопасный режим», «Защита», «Активно», «Используется», «Роли», «Назначение» при установке — НЕ РЕАЛИЗУЕМ в этом релизе

Пакетный режим конфигуратора (`/LoadCfg "файл.cfe" -Extension "имя"` + `/UpdateDBCfg`) не имеет ключей установки этих свойств; утилита `ibcmd config load --extension` — тоже. Свойства выставляются только через COM-объектную модель (Windows-only) либо вручную в Конфигураторе. На Avalonia/Linux COM отсутствует — фича была бы Windows-only.

Готовая формулировка комментария:

> @RafaIS, спасибо за предложение! Разобрал техническую сторону. Флажки «Безопасный режим», «Защита», «Активно», «Используется», «Роли» и поле «Назначение» нельзя задать через пакетный режим Конфигуратора или ibcmd — у этих инструментов таких ключей просто нет. Единственный способ выставить их программно — COM-объектная модель платформы, которая работает только на Windows и только при зарегистрированном COM-коннекторе (в Linux-версии приложения COM недоступен в принципе).
>
> Поэтому в текущем релизе сделаны остальные пункты: исправлено автозаполнение имени расширения при выборе файла, список расширений перенесён наверх и получается заранее (при открытии окна и при смене базы), перед установкой выполняется проверка уже установленных расширений с выводом плана в журнал. Управление свойствами расширения зафиксировал как отдельную задачу: если сделаем, то это будет Windows-only COM-операция (флажки появятся в окне установки, но в Linux-версии останутся недоступны). Напишите, подходит ли такой формат.
