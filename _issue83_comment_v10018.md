Исправлено в версии **1.0.1.8** (Windows) — новый подход:

Ключевой факт из вашего репорта: `where ring` в обычной командной строке работает, а приложение `ring` не находит. Значит, **PATH процесса приложения отличается от PATH пользовательской консоли** (автозапуск, планировщик, ярлык с изменённым окружением). Предыдущие правки искали «где искать» в PATH процесса — и честно повторяли его отсутствие.

В 1.0.1.8 построитель кандидатов поиска `ring` работает так:
1. **PATH процесса** — как раньше;
2. **свежий PATH из реестра** — `HKCU\Environment\Path` + `HKLM\...\Session Manager\Environment\Path` (с разворачиванием `REG_EXPAND_SZ`) — это PATH «будущей» консоли пользователя, тот самый, где `where ring` находит;
3. **известные каталоги 1С** — `bin` платформы рядом с найденным `rac`, `%LOCALAPPDATA%\1C\1cv8\`, `C:\Program Files\1cv8\<версия>\bin` (ищутся `ring.exe`, `ring.cmd`, `ring.bat`).

Найденный `ring` запускается **по полному пути** (`.cmd`/`.bat` — через `cmd.exe /c`, как в консоли пользователя) — **перезапуск приложения больше не требуется**. Если `ring` найден по реестровому PATH, но отсутствует в PATH процесса, в подсказке по-прежнему появится совет перезапустить приложение.

Диагностика `CM_RAC` усилена: при неудаче в журнал пишутся каталоги, по которым искали, и факт «PATH процесса: N элементов, реестровый PATH: M» — отличие окружения станет видимым с первого сообщения.

Покрыто тестами [`Issue83RingPathRegistryTests.cs`](Workspace1C.Tests/Issue83RingPathRegistryTests.cs).

Релиз: https://github.com/sivatorov/Workspace1C/releases/tag/v1.0.1.8

Проверьте, пожалуйста, в 1.0.1.8: перезапустите приложение (PATH процесса мог устареть с прошлого запуска) и откройте вкладку «Лицензии» — лицензии должны либо появиться, либо вкладка покажет список проверенных источников PATH.
