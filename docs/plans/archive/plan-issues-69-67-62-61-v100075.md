## 1. Issue #69 — «Удаление из кластера» (без комментариев, правки по описанию) · объём M

### 1.1. Контекст и корень проблемы (по коду 1.0.0.74)

1. Удаление ИБ из кластера: [`ServerMonitorViewModel.DropSelectedInfobaseAsync`](Workspace1C/ViewModels/ServerMonitorViewModel.cs:681) вызывает `_rac.DropInfobaseAsync(BuildParams(), clusterId, row.InfobaseId, dropDatabase)`. При `!ok` — `ShowWarningOnUi(DropFailed + detail, DropTitle)` — обычный MessageBox с единственной кнопкой **OK**.
2. Сигнатура [`IRacClient.DropInfobaseAsync`](Workspace1C/Services/IRacClient.cs:178) НЕ принимает учётные данные администратора ИБ (`infobaseUser`/`infobasePassword`), в отличие от [`GetInfobaseInfoAsync`](Workspace1C/Services/IRacClient.cs) — а rac-команда `infobase drop` на защищённой базе требует аутентификацию администратора ИБ, иначе возвращает ошибку (скриншот пользователя). [`RacConnectionParams`](Workspace1C/Services/IRacClient.cs:15) несёт только адрес/порт/логин администратора КЛАСТЕРА (RAS).
3. Пользователь (без комментариев — по описанию): «Диалог хороший, но тут должно было быть 2 поля Логин и пароль и не ОК, а „Повторить попытку“ и „Отмена“. По „Повторить попытку“ пробуем с логином паролем».

### 1.2. Конкретные правки

1. **Сервис rac.** Расширить `IRacClient.DropInfobaseAsync` необязательными параметрами `string? infobaseUser = null, string? infobasePassword = null` (как у `GetInfobaseInfoAsync`) и реализацию [`RacClient.DropInfobaseAsync`](Workspace1C/Services/RacClient.cs:870): сборка аргументов `--infobase-user=...` / `--infobase-password=...` по образцу сборки для `GetInfobaseInfoAsync`; пароль не писать в журнал (существующий `SensitiveDataMasker`). `LastActionError` остаётся доступным для показа в диалоге.
2. **ViewModel.** В [`ServerMonitorViewModel`](Workspace1C/ViewModels/ServerMonitorViewModel.cs:681):
   - при `!ok` или исключении вместо простого предупреждения — показать **диалог повтора** с текстом ошибки (`detail`), полями «Логин»/«Пароль», кнопками «Повторить попытку»/«Отмена»;
   - «Повторить попытку» → `DropInfobaseAsync(BuildParams(), clusterId, row.InfobaseId, dropDatabase, infobaseUser, infobasePassword)`; повторная ошибка → снова тот же диалог (с сохранённым логином, без пароля), «Отмена» → выход;
   - успех → статус `ServerMonitor.Infobase.Status.DroppedFormat`, `Refresh()`.
   - Механизм показа диалога — через инжектируемый сервис окон (по образцу того, как окно монитора открывает `RacInfobaseEditWindow`/`LoadInfobaseInfoAsync` с кредами в `RacInfobasePropertiesWindow`), чтобы VM оставалась тестируемой.
3. **View WPF.** Новое окно `RacInfobaseDropRetryWindow` (по образцу [`RacInfobaseDropWindow.xaml.cs`](Workspace1C/Views/RacInfobaseDropWindow.xaml.cs)): подпись «Не удалось удалить базу: <детали>», поля «Логин», «Пароль», кнопки «Повторить попытку» (default) и «Отмена»; свойство результата `(string? User, string? Password)`.
4. **View Avalonia.** `RacInfobaseDropRetryWindow.Avalonia.cs` — то же окно на Avalonia (код-билдер, без разметки), стили темы.
5. **Локализация ru/en:** `ServerMonitor.Infobase.Drop.RetryTitle`, `RetryPrompt`, `RetryLogin`, `RetryPassword`, `RetryButton`, `CancelButton`.
6. **Тесты:**
   - `RacClientTests` (расширить): аргументы `infobase drop` содержат `--infobase-user=/--infobase-password=`; пароль не появляется в журнале; сигнатура без кредов не даёт новых аргументов (регресс).
   - `ServerMonitorViewModelTests` (расширить/новый): fake rac первый вызов `DropInfobaseAsync` → false, после ввода кредов — вызов с `infobaseUser`/`infobasePassword`, статус Dropped; «Отмена» → второй вызов НЕ выполняется; повторная ошибка → снова диалог.
   - Разметочный страж (по образцу `Issue41WindowLayoutTests`): в WPF-окне `RacInfobaseDropRetryWindow` есть поля Логин/Пароль и кнопки «Повторить попытку»/«Отмена»; Avalonia-окно содержит те же элементы.

### 1.3. Риски и зависимости

- Не задевать создание/изменение ИБ и удаление с БД — диалог повтора только для ветки `DropSelectedInfobaseAsync` (но при желании той же логикой можно покрыть `CreateInfobaseAsync`/`UpdateInfobaseAsync` — вне рамок текущего комментария).
- Пароль администратора ИБ — только в памяти (как `RacConnectionParams.Password`), не сериализуется.
- Пересечение с #61: новое окно сразу писать с `FormLabelBrush`-подписями.

## 2. Issue #61 — «Цвета заголовков в тёмной версии» (последний комментарий НЕ от владельца) · объём L

### 2.1. Контекст и корень проблемы

1. В 1.0.0.74 `FormLabelBrush` применён ТОЛЬКО в [`WpfUi.Label`](Workspace1C/Views/WpfUi.cs:52) и [`AvaloniaUi.Label`](Workspace1C/Views/AvaloniaUi.Avalonia.cs:42). Пользователь тестирует именно 1.0.0.74 (в #62/#67 видит фичи 1.0.0.74) и сообщает: «Результат всё тот же — на всех, указанных ранее скринах, окнах».
2. Гипотезы (проверить и устранить системно):
   - Подписи полей строятся не только через `Label`: `WpfUi.Text(..., secondary: true)`, `Field(...)`, `MakeLabel`, `Header`, прямые `TextBlock` в XAML/axaml с фиксированным тёмным `Foreground`;
   - вторичная кисть (`secondary: true`) в пользовательских/сгенерированных схемах может оставаться тёмной в тёмной теме (генерируемые словари схемы строятся из палитр — новый ключ `FormLabelBrush` мог не попасть в генерируемые темы);
   - часть окон построена прямым XAML- кодом строй (не через `WpfUi`), где подписи наследуют дефолт.

### 2.2. Конкретные правки

1. **Шаг-гейт/коммуникация:** в комментарии о релизе попросить, если что-то останется после 1.0.0.75, указать версию из «О программе» и скриншот конкретного окна; сами правки делать по коду (они безопасны).
2. **Единая точка подписи** (обе платформы):
   - `WpfUi`: `Text(...)` для подписей полей и `Label` — всегда `FormLabelBrush`; добавить перегрузки/методы `FieldLabel`/`MakeLabel` там, где они есть, чтобы все подписи полей шли через кисть формы;
   - `AvaloniaUi`: то же (Text/Label/Header/Field).
   - WPF XAML: ввести Style/проверку для `TextBlock`-подписей в формах (`Foreground={DynamicResource FormLabelBrush}` по умолчанию для шаблонов подписей полей, если используется отдельный стиль).
3. **Генерация схем:** проверить `ColorScheme`/`ThemeManager` (WPF и Avalonia): в динамически генерируемые словари тем добавляется ключ `FormLabelBrush` (из палитры primary текста), чтобы пользовательские схемы не «теряли» кисть.
4. **Аудит по реестру:** пройти окна, повторяющие скриншоты пользователя (#61: «все пять полей», «заголовки полей ввода») — кандидаты: формы настроек ИБ (`ConnectionSettingsWindow`), монитор сервера (`ServerMonitorWindow`), свойства базы (`RacInfobasePropertiesWindow`), миграция, публикация; заменить фиксированные тёмные `Foreground` (список hex расширить: `#000000, #111827, #0F172A, #1C1917, #1F2937, #1E293B`, `Black`, `Gray`) на `FormLabelBrush`; исключения (текст на акцентных плашках, ошибки) — в белый список стражей.
5. **Тесты:**
   - `Issue61DarkPaletteAuditTests` (расширить): больший набор тёмных hex; поиск по `*.xaml`/`*.axaml` и построителям `WpfUi`/`AvaloniaUi` (`Field`/`Header`/`MakeLabel`/`Text` для подписей);
   - `ThemeFormLabelTests` (расширить): `FormLabelBrush` во ВСЕХ генерируемых схемах (переданные палитры), WCAG-контраст ≥ 4.5 на Card/Input фоне в обеих темах;
   - снимок реестра аудита → перечень заменённых мест в комментарий issue + release notes.

### 2.3. Риски

- Без скриншота остаётся риск «чинить не то окно» — поэтому полный системный аудит построителей (покрывает класс проблем), а не точечная правка одного окна.
- Не задеть намеренно светлые подписи на плашках (белый список).

## 3. Issue #62 — «Правка меню трея» (последний комментарий НЕ от владельца) · объём M

### 3.1. Контекст и корень проблемы

1. В 1.0.0.74 каталог иконок трея = каталог «Утилит»; WPF-адаптер для групп уже передаёт `iconKey`/`iconColor` в `CreateTrayItem` ([`MainWindow.Tray.cs:313/462/506/640`](Workspace1C/Views/MainWindow.Tray.cs:312)). Пользователь: «выбор большой. Но до трея он не доходит… Теперь другая иконка, но она всё ещё не меняется при выборе в настройках».
2. Гипотезы:
   - Меню трея пересобирается при показе (`Opening`), но layout читается из КЭША в MainWindow; после сохранения в редакторе трея (`TrayMenuEditorWindow`) кэш не инвалидируется → в трее старый layout (иконка не меняется);
   - выбранный в редакторе `IconKey`/`IconColor` не попадает в сериализуемый JSON (`tray_menu_layout.json`) или не доходит до узла группы;
   - `IconKeyToGeometryConverter.ResolveGeometry(iconKey)` не резолвит часть ключей общего каталога → фолбэк «совсем другая иконка» (проверить покрытие, см. `IconSetCoverageTests`).

### 3.2. Конкретные правки

1. **Инвалидация кэша layout/пересборка меню:** после сохранения настроек в редакторе трея (и применения) — `MainWindow` (WPF): пересоздать `_trayIcon.ContextMenuStrip = CreateMainTrayMenu()`; Avalonia: пересобрать `NativeMenu`. Найти точку сохранения (`TrayMenuEditorViewModel.Apply...`/окно) и пробросить событие/вызов в MainWindow.
2. **Сериализация:** проверить модель `TrayMenuItem`/`TrayMenuLayout` ([`TrayMenuLayout.cs:80`](Workspace1C/Models/TrayMenuLayout.cs:80)) и [`TrayMenuBuilder.cs:66`](Workspace1C/Services/TrayMenuBuilder.cs:66): `IconKey`/`IconColor` группы сохраняются в JSON и восстанавливаются при чтении (тест round-trip).
3. **Резолвинг ключей:** покрыть `IconKeyToGeometryConverter.ResolveGeometry` ВСЕ ключи каталога `UtilitiesMenuCatalog.All` (расширить `IconSetCoverageTests`); для нерезолвимых ключей — либо таблица соответствий в геометрии, либо фильтр каталога в редакторе трея (не показывать то, что не применится).
4. **Превью=применение:** редактор трея показывает иконку той же функцией, что применяет адаптер (единый путь).
5. **Тесты:**
   - round-trip `IconKey`/`IconColor` через JSON layout;
   - исходниковый страж: после `Save` в редакторе трея вызывается пересоздание меню (сигнатура/событие);
   - `TrayMenuIconCatalogTests` (расширить): все ключи каталога резолвятся в геометрию WPF; Avalonia `IconHelper` резолвит те же ключи.

### 3.3. Риски

- Linux `NativeMenu` не поддерживает цветные иконки (уже отмечено в 1.0.0.74) — для Avalonia достаточно коррекции каталога/превью, без имитации цветных иконок.
