## A. Issue #79 «Развернуть тестовую копию» — ошибка после создания базы и загрузки данных

### Контекст
- v1.0.1.39 уже добавил в общий catch [`TestDeployService.cs`](Workspace1C/Services/TestDeployService.cs:242) цепочку
  InnerException (`DescribeException`) и тип+стек в журнал окна. Новый комментарий 7OH (2026-11-06):
  ошибка возникает **уже после создания базы и загрузки данных**; приложены скриншот и
  `diagnostics_20261106_164640.zip`. Пользователь сообщает, что **блокировка заданий у итоговой базы
  в кластере включена** (т.е. шаг «Отключить регламентные задания» отработал/частично отработал).

### Шаг A1. Анализ диагностики (обязательно первым делом)
1. Скачать ZIP из issue #79 (вложение к последнему комментарию; через GitHub API assets или страницу issue).
2. Найти в логе журнала окна: последнюю строку шага до ошибки (`TestDeploy.Step.DisableJobs` /
   `TestDeploy.Step.Markers` / `TestDeploy.Step.AddToGroup`), тип исключения и стек
   (их пишет обработчик [`TestDeployService.cs:253-255`](Workspace1C/Services/TestDeployService.cs:253)).
3. По стеку определить точное место; зафиксировать вывод в комментарии к issue.

### Диагноз (по коду, до разбора ZIP)
Шаги после Restore ([`TestDeployService.cs:205-235`](Workspace1C/Services/TestDeployService.cs:205)):
- **Шаг 5 DisableJobs** — [`DisableScheduledJobsAsync`](Workspace1C/Services/TestDeployService.cs:480):
  вызывает [`ScheduledJobsService.SetAllAsync`](Workspace1C/Services/ScheduledJobsService.cs:164) →
  [`ComScriptRunner.RunAsync`](Workspace1C/Services/ComScriptRunner.cs) (COM-подключение к целевой базе).
  Внутри метода свой try/catch → ошибки превращаются в **warning** и развёртывание продолжается —
  ошибка «Внутренняя ошибка» сюда не попадает, НО: «Внутренняя ошибка» — это типовой текст ошибки
  самой COM-компоненты 1С; если `ComScriptRunner` вернул failure — пользователь увидит warning,
  а не ошибку. Значит ошибка — **после** этого шага, т.е. шаг 6/7 или пост-обработка окна.
- **Шаги 6–7 (Markers/AddToGroup)** — тривиальные, падение маловероятно.
- **Пост-обработка окна** — [`TestDeployWindow.cs:753-820`](Workspace1C/Views/TestDeployWindow.cs:753):
  после успеха сервиса выполняются `TestDeployStore.Upsert(scenario)`,
  [`TestDeployScheduleHelper.RegisterTask`](Workspace1C/Services/TestDeployScheduleHelper.cs:19),
  `TestDeployPlanner.EnsureGroup`; их catch (строка ~819) показывает голый `ex.Message` —
  подходит под симптом «ошибка после загрузки данных».

### Что сделать
1. **Разнести обработку ошибок по шагам 5–7**: обернуть каждый шаг (DisableJobs/Markers/AddToGroup)
   в локальный try/catch, который формирует `result.ErrorMessage = Fail(<шаг>, …)` и добавляет в
   `result.Log` строку с шагом — вместо общего `TestDeploy.Step.Unknown` в
   [`TestDeployService.cs:251`](Workspace1C/Services/TestDeployService.cs:251). Общий catch остаётся
   страховкой, но шаг теперь будет виден в любом сообщении.
2. **Пост-обработка окна**: в catch обоих окон
   ([`TestDeployWindow.cs:819`](Workspace1C/Views/TestDeployWindow.cs:819),
   `TestDeployWindow.Avalonia.cs:658`) писать тип/стек в журнал окна и лог приложения, сообщение —
   через `DescribeException`-подобное разворачивание InnerException.
3. **Корневой фикс по данным ZIP** (варианты по вероятности):
   - если падает `TestDeployStore.Upsert`/`RegisterTask` — защитить try/catch с warning в журнал
     (сценарий/расписание не должны ронять успешное развёртывание);
   - если падает COM-скрипт выключения заданий при уже применённой блокировке — в
     `ScheduledJobsService`/`ComScriptRunner` добавить расшифровку типовой ошибки
     «Внутренняя ошибка» (через [`ConsoleOutputDecoder`](Workspace1C/Services/ConsoleOutputDecoder.cs)
     если применимо) и повторную пробу с уточнённым сообщением;
   - если падает `EnsureGroup`/применение результата — исправить конкретное место.
4. Если по ZIP причина неоднозначна — задать уточняющий вопрос в issue (приложить, что увидели в стеке).

## B. Issue #109 «Очистка кэша» — пользовательский кеш по нулям для всех баз

### Диагноз (по коду)
- Junction-фикс v1.0.1.39 ([`OneCCacheCleaner.GetDirectorySize`](Workspace1C/Services/OneCCacheCleaner.cs:780),
  [`TryDeleteDirectory`](Workspace1C/Services/OneCCacheCleaner.cs:936)) уже в коде, но 7OH
  сообщает: очистка **пользовательского кеша по нулям для всех баз**.
- Корни кеша — [`GetCacheRoots`](Workspace1C/Services/OneCCacheCleaner.cs:858):
  Windows — только `%LOCALAPPDATA%\1C\1cv8` (программный) и `%APPDATA%\1C\1cv8` (пользовательский).
  Не покрытые сценарии:
  1. **Перенос junction-ом на уровне родителя**: если ссылкой заменён сам каталог `1C`
     (или `%APPDATA%\1C` целиком) — перечисление через junction работает, но если пользователь
     перенёс кеш **копированием** и оставил настройки 1С указывать на другой диск — корней нет вовсе.
  2. **Легаси-пути 8.2**: `%APPDATA%\1C\1Cv82` / `%LOCALAPPDATA%\1C\1Cv82`.
  3. **Нестандартное расположение**: у 1С нет штатной настройки переноса, пользователи делают
     junction в разных местах; нужен универсальный пользовательский путь.

### Что сделать
1. **Дополнительные корни кеша в настройках** (ключевая правка по просьбе пользователя):
   - [`AppSettings.cs`](Workspace1C/Models/AppSettings.cs:480): новое поле
     `List<string> AdditionalCacheRoots` (пути к каталогам, где 1С хранит кеш; по умолчанию пусто);
   - Настройки → существующая секция «Очистка кэша»/поведение: поле «Дополнительные каталоги кеша 1С»
     (список путей, кнопки добавить/удалить) — WPF [`SettingsWindow.xaml.cs`](Workspace1C/Views/SettingsWindow.xaml.cs)
     и Avalonia [`SettingsWindow.Avalonia.cs`](Workspace1C/Views/SettingsWindow.Avalonia.cs);
     применение — статический `OneCCacheCleaner.SetAdditionalRoots(...)` при старте и после настроек;
   - [`GetCacheRoots`](Workspace1C/Services/OneCCacheCleaner.cs:858) дополняет выдачу дополнительными
     корнями (для `kind` не фильтровать программный/пользовательский — в доп. корнях ищем всё).
2. **Легаси-корни**: добавить `1Cv82`-варианты для обоих типов кеша на Windows.
3. **Диагностика «нулей»**: при вычислении размеров (GetSize/GetOrphanSize) при включённом логировании
   писать в журнал список корней, которые проверялись, и сколько каталогов кеша найдено
   (`LogCategory` по образцу issue #80) — чтобы в следующей диагностике ZIP сразу было видно,
   где искали и почему 0.
4. **Убедиться, что junction-поддержка покрывает корень целиком**: `EnumerateCacheDirectories`
   ([`OneCCacheCleaner.cs:730`](Workspace1C/Services/OneCCacheCleaner.cs:730)) при
   `Directory.GetDirectories(root)` уже проходит через junction-корень; отдельно проверить сценарий,
   когда junction стоит на каталоге **версии** (`root\8.3.xx` → ссылка) — перечисление версий должно
   находить каталоги за ссылкой (/manual-рекурсия уже справляется, покрыть тестом).
5. **Открытие папок кеша (#110, см. секцию C)** — экспортировать публичный API перечисления:
   `public static IReadOnlyList<string> GetCacheDirectories(Infobase, OneCCacheKind)` (обёртка над
   internal `EnumerateCacheDirectories`), используется и очисткой, и «открыть папку».

### Тесты (`Workspace1C.Tests`)
- Доп. корни: база с кешем в нестандартном корне (temp-каталог) → размер > 0, очистка удаляет.
- Junction на каталоге версии: размер считается, удаление не ломает ссылку (как в v1.0.1.39).
- Легаси-корень `1Cv82`: каталог найден.
- Чистка temp-каталогов в finally; Windows-only junction-тесты помечены и скипаются на CI-Linux.

### Риски
- Деструктивные операции в пользовательских каталогах → очистка только каталогов, совпадающих по
  имени с известными именами кеша баз (существующая логика `GetCacheNames`), корни целиком не удалять.
