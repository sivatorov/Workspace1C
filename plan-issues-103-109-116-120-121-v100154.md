## 2. Задача 1 — Issue #109а: неверный расчёт размера кэша (15 МБ vs 15 ГБ)

### Текущее состояние кода

- Размеры считаются в [`OneCCacheCleaner.cs`](Workspace1C/Services/OneCCacheCleaner.cs):
  - [`GetSize(OneCCacheKind, IEnumerable<Infobase>)`](Workspace1C/Services/OneCCacheCleaner.cs:733) —
    суммарный размер по каталогам, **сопоставленным текущим базам**
    ([`EnumerateCacheDirectories`](Workspace1C/Services/OneCCacheCleaner.cs:765));
  - [`GetDirectorySize`](Workspace1C/Services/OneCCacheCleaner.cs:836) — ручная рекурсия
    с обходом junction/symlink по цели и защитой от циклов (v1.0.1.39);
  - сопоставление баз — имена каталогов: GUID из карты `IdConnStrMap`,
    `Srvr__<сервер>__Ref__<база>__` ([`GetClientServerDirNames`](Workspace1C/Services/OneCCacheCleaner.cs:391)),
    ID базы и легаси-имя ([`GetCacheNames`](Workspace1C/Services/OneCCacheCleaner.cs:433));
  - корни: [`GetCacheRoots`](Workspace1C/Services/OneCCacheCleaner.cs:916) —
    Windows: `%LOCALAPPDATA%\1C\1cv8` (Program), `%APPDATA%\1C\1cv8` + `1Cv82` (User),
    легаси `%LOCALAPPDATA%\1C\1Cv82`, дополнительные корни из `AppSettings.AdditionalCacheRoots`;
    Linux: `~/.cache/1cv8`, `~/.local/share/1cv8`, `~/.1cv8/1C/1cv8`.
- Локализация кеша в каталогах версий поддержана: `1cv8\<версия>\<имя>` —
  [`EnumerateCacheDirectories`](Workspace1C/Services/OneCCacheCleaner.cs:805).
- Диагностика: журнал по категории `CM_CACHE` ([`LogCategory.cs`](Workspace1C/Services/LogCategory.cs:65)),
  в том числе лог матчера размеров ([`OneCCacheCleaner.cs`](Workspace1C/Services/OneCCacheCleaner.cs:772)).

### Гипотезы причины «показывает 15 МБ, а по факту 15 ГБ» (проверить по порядку)

1. **Размер считается только по каталогам, сопоставленным базам** —
   [`GetSize`](Workspace1C/Services/OneCCacheCleaner.cs:733) суммирует лишь найденные
   `EnumerateCacheDirectories`. Каталоги кеша, не сопоставленные ни одной базе
   (нестандартные имена, «осиротевший» кэш, кэш версий), в «общий объём» не попадают.
   Реальный объём корней кэша ~15 ГБ складывается из «непринадлежащих» каталогов.
2. **Сопоставление по карте/именам не отработало** (серверные базы: имена каталогов
   `Srvr__…__Ref__…__` зависят от `Server`/`DatabaseName`; при пустом имени БД —
   [`GetClientServerDirNames`](Workspace1C/Services/OneCCacheCleaner.cs:397) вернёт пусто).
3. **Перечисление подкаталогов версий**: если кеш лежит на глубине больше одного уровня
   версий (`1cv8\<версия>\<версия-подкаталог>\<имя>`) либо корень сам является junction —
   проверить, что `Directory.GetDirectories(root)` и匹配 не режут варианты.
4. **Формат отображения** (ФорматSize/единицы) — маловероятно, но проверить конвертацию
   байтов в строку в окне очистки кэша.

### Что сделать

1. **Диагностика (первый шаг, без правок)**: собрать ZIP-диагностику у репортёра
   (флаг `CM_CACHE=1`): лог перечисляет корни
   ([`OneCCacheCleaner.cs`](Workspace1C/Services/OneCCacheCleaner.cs:772)),
   число найденных каталогов и суммарный размер. Сравнить с фактическим объёмом корней
   на диске (du/Powershell). Если суммы сходятся по каталогам баз, но не с «фактом» —
   причина в п.1 гипотез (несопоставленные каталоги).
2. **Показывать честный общий объём кэша**: в окне/отчёте очистки кэша добавить
   (или исправить) строку «общий объём кэша» как сумму **всех** каталогов в корнях кэша
   (включая несопоставленные базе), а размер по базам оставить отдельной строкой.
   Реализация: новый метод [`OneCCacheCleaner.cs`](Workspace1C/Services/OneCCacheCleaner.cs)
   `GetRootTotalSize(OneCCacheKind)` — рекурсивно по корням `GetCacheRoots`
   (+`AdditionalCacheRoots`), junction-safe через [`GetDirectorySize`](Workspace1C/Services/OneCCacheCleaner.cs:836).
3. **Усиление сопоставления каталогов базам** (если диагностика покажет п.2):
   - в [`GetClientServerDirNames`](Workspace1C/Services/OneCCacheCleaner.cs:391) —
     при пустом `DatabaseName` пробовать имя каталога ИБ / GUID;
   - поддержка вложенности каталогов версий глубже одного уровня в
     [`EnumerateCacheDirectories`](Workspace1C/Services/OneCCacheCleaner.cs:805)
     (обход поддерева версий рекурсивно, `IsVersionDirName` уже есть —
     [`OneCCacheCleaner.cs`](Workspace1C/Services/OneCCacheCleaner.cs:482)).
4. **Единицы отображения**: проверить форматтер размера (МБ/ГБ) в окне очистки
   ([`MainViewModel.Tools.cs`](Workspace1C/ViewModels/MainViewModel.Tools.cs:1391) —
   блок очистки кэша; Avalonia — [`MainViewModel.Avalonia.Tools.cs`](Workspace1C/ViewModels/MainViewModel.Avalonia.Tools.cs:1576)):
   исключить целочисленное деление, теряющее ГБ.
5. Локализация ru/en для новых строк окна очистки кэша (`Cache.*`).

### Файлы для изменения

- [`Workspace1C/Services/OneCCacheCleaner.cs`](Workspace1C/Services/OneCCacheCleaner.cs) —
  `GetRootTotalSize`, усиление `EnumerateCacheDirectories`/`GetCacheNames`
- [`Workspace1C/ViewModels/MainViewModel.Tools.cs`](Workspace1C/ViewModels/MainViewModel.Tools.cs:1391) —

## 3. Задача 2 — Issue #109б: серверный кэш, перенесённый через реестр

### Постановка (Nodon84, 2026-11-11 08:47:10)

«Если серверный кэш перенести на другой диск (перенос через параметры в реестре),
то он не виден». Сейчас [`GetCacheRoots`](Workspace1C/Services/OneCCacheCleaner.cs:916)
учитывает только фиксированные корни + `AdditionalCacheRoots` (ручной ввод в настройках)
— **реестровые параметры 1С не читаются вовсе**.

### Что сделать

1. **Исследовать и закодировать чтение реестровых корней 1С** (Windows-only, #if WINDOWS):
   - источник паттерна чтения ключей 1С: [`OneCTemplateService.cs`](Workspace1C/Services/OneCTemplateService.cs:264)
     (перебор вариантов `Software\1C\1cv8\1cestart`, `Software\1C\1Cv8\1cestart`,
     `Software\1C\1cv8\Common`, `Software\1C\1Cv8\Common` — реестр и с C и с v8x-вариантами);
   - целевые ключи для местоположений данных/кэша платформы: `HKEY_CURRENT_USER\Software\1C\1Cv8`
     (и `Software\1C\1cv8`), включая ветки конкретных версий `8.3…`; искать строковые
     значения, задающие каталоги данных/кэша (перебор известных имён значений +
     диагностический дамп всех значений ветки при `CM_CACHE`);
   - также проверить `HKEY_LOCAL_MACHINE\SOFTWARE\1C\1Cv8` для общесерверных настроек.
2. **Расширить [`GetCacheRoots`](Workspace1C/Services/OneCCacheCleaner.cs:916)**:
   новая internal-функция `GetRegistryCacheRoots()` (Windows) → пути из реестра
   добавляются в корни Program/User по флагу `kind`; кэшировать результат на сеанс
   (реестр читается 1 раз, как `SetAdditionalRoots`).
   - Linux-версия: no-op (реестра нет), поведение не меняется.
3. **Fallback на настройки сохраняется**: найденные реестровые пути — дополнение к
   `AdditionalCacheRoots`, не замена; дубликаты путей отбрасывать (сравнение
   нормализованных путей, junction-цели канонизировать через
   [`ResolveCanonicalPath`](Workspace1C/Services/OneCCacheCleaner.cs:885)).
4. **Диагностика**: логировать в `CM_CACHE` список реестровых ключей/значений,
   из которых взяты корни (для репорта «не виден» будет видно, что нашли/не нашли).
5. **Очистка junction-целей** уже junction-safe (v1.0.1.39:
   [`TryDeleteDirectory`](Workspace1C/Services/OneCCacheCleaner.cs:1028) — удаляется
   содержимое цели, ссылка остаётся) — при переносе кэша в реестр+mklink схема работает.
6. При невозможности однозначно определить имя реестрового значения — консервативно:
   не добавлять путь в корни очистки, но показывать в диагностике (не удалить лишнее).

### Файлы для изменения

- [`Workspace1C/Services/OneCCacheCleaner.cs`](Workspace1C/Services/OneCCacheCleaner.cs) —
  `GetRegistryCacheRoots` + интеграция в `GetCacheRoots` (#if WINDOWS/#if LINUX)
- при необходимости новый сервис `Workspace1C/Services/OneCCacheRegistryLocations.Windows.cs`
  (чистая функция чтения реестра, тестируемая с подменённым ключом)
- [`Workspace1C/Services/LogCategory.cs`](Workspace1C/Services/LogCategory.cs:65) —
  расширение диагностики (обычно без правок)

**Тесты:** юнит-тесты на дедупликацию корней (реестр + настройки + фиксированные),
на junction-цель как корень; Windows-only реестровая часть — ручная проверка
(перенос серверного кэша через реестр на тестовой машине) + source-гварды.
