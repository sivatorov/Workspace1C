## 1. Issue #97 — «Ошибка интерфейса» (клик по второй найденной базе)

### Суть (строго по описанию, комментариев нет)
В поиске есть текст «Отобрано 2 базы» (плоский список «Найдено (N)» при активном
фильтре — [`IsFilterModeActive`](Workspace1C/ViewModels/MainViewModel.Avalonia.cs:1141)).
Клик по одной базе — ок, по второй — «вот такое окно» (некорректное окно).
Скриншот из issue недоступен локально (GitHub user-attachments → 403).

### Предполагаемая причина
В [`BuildRowCard`](Workspace1C/Views/MainWindow.Avalonia.Tree.cs:580) база `ib`
**захлопывается в замыкания** обработчиков:
- `card.DoubleTapped` (строка 580) — запуск базы,
- `cell.DoubleTapped` колонки «Версия» (строка 505, `PickPlatformVersionFor`) и
  «Конфигурация»/«№ релиза» (строка 517, `OpenPropertiesOnPlatformTab`),
- `card.PointerPressed` Ctrl+клик (строка 600).

Avalonia **переиспользует контейнеры** дерева при пересборке плоского списка
(поиск перестраивает список на каждый ввод символа). Контейнер, созданный для
первой базы, переиспользуется для второй, но замыкания продолжают ссылаться на
**старую** `ib`: клик по второй базе срабатывает по данным первой — открывается
окно/запуск не той базы (в т.ч. окно выбора платформы, если у «старой» базы не
задана версия). Аналогичная механика уже фиксировалась ранее (issue #35:
«при активном отборе контейнер строки не пересоздаётся и привязки не
перечитывали бы обновлённые значения» — [`MainViewModel.Commands.cs:295`](Workspace1C/ViewModels/MainViewModel.Commands.cs:295)).

### Правки
Файл: [`Workspace1C/Views/MainWindow.Avalonia.Tree.cs`](Workspace1C/Views/MainWindow.Avalonia.Tree.cs)

1. В обработчиках `BuildRowCard` (строки 505–509, 517–521, 580–595, 600–608) брать
   базу **в момент события** из `DataContext` карточки/ячейки:
   `if ((sender as Control)?.DataContext is not Infobase ib) return;`
   вместо замыкания на параметр метода. Надёжный вариант — локальная функция
   `Infobase? ResolveIb(object? sender)`, общий для всех трёх обработчиков.
2. Проверить аналогичные замыкания на `ib` в том же файле (обработчики тегов,
   кнопок строки `RowActionButton`) — при наличии того же паттерна исправить
   единообразно (минимально: только там, где обработчик открывает окно/запускает
   команду с захваченной `ib`).

### Риски
- Низкие: меняется только источник данных события (DataContext вместо замыкания);
  DataContext карточки всегда равен текущей строке списка.
- Скриншот не анализировался — гипотеза основана на коде и истории issue #35.
  Если после фикса автор issue подтвердит проблему, запросить текст окна.

### Критерии проверки
1. Ввести в поиск текст, дающий ровно 2 базы; поочерёдно двойной клик по каждой —
   запускается/открывается именно та база, по которой кликнули.
2. Изменить текст поиска (пересборка списка), повторить клики — результат корректен.
3. Двойной клик по колонкам «Версия» и «Конфигурация» обеих найденных баз — окно
   открывается для правильной базы.
4. Ctrl+клик по обеим базам — закладка ставится правильной базе.

## 2. Issue #92 — выгрузка списка баз в *.dt (серверная база)

### Суть (по последнему комментарию 7OH, 2026-11-01 11:58)
«По прежнему не может выгрузить серверную базу данных». Лог окна:
- «Demo 27» — Профиль СУБД не задан — получение данных СУБД из кластера (rac)…
- База «Demo_8.3.27» не найдена в кластерах сервера localhost — операция может
  завершиться ошибкой подключения к СУБД
- операция завершилась ошибкой (1 сек) — **без текста ошибки**.

(Запрос aepkugesi от 2026-10-31 о завершении сеансов/блокировках перед выгрузкой —
большая отдельная фича, в 1.0.1.17 не входит; зафиксировать в комментарии.)

### Предполагаемые причины
1. **Текст ошибки не попадает в журнал окна**: при неудаче
   [`BatchOperationsViewModel.cs:433`](Workspace1C/ViewModels/BatchOperationsViewModel.cs:433)
   пишет только «операция завершилась ошибкой (N сек)», хотя `result.Error`/
   `result.Output` уже сохранены в `item.StatusText` (строки 429–431). Пользователь
   не видит причину.
2. **rac-резолвер диагностируется только по исключениям**:
   [`ClusterInfobaseCredentialsResolver.ResolveAsync`](Workspace1C/Services/ClusterInfobaseCredentialsResolver.cs:109)
   молча `continue` при пустом/не содержащем нужную базу списке ИБ кластера —
   не видно, какие имена вообще вернул rac (совпадение — по имени ИБ
   `connection.DatabaseName` = Ref).
3. После неудачного резолва операция **продолжается без данных СУБД** — ibcmd
   закономерно падает (гарантированная ошибка вместо быстрого понятного отказа).

### Правки
1. [`Workspace1C/ViewModels/BatchOperationsViewModel.cs`](Workspace1C/ViewModels/BatchOperationsViewModel.cs:425):
   в строку журнала об ошибке включать причину — `result.Error` либо обрезанный
   `result.Output` (как в `item.SetStatusText`). Новая строка вида
   `«{name}» — операция завершилась ошибкой ({elapsed}): {причина}`.
2. [`Workspace1C/Services/ClusterInfobaseCredentialsResolver.cs`](Workspace1C/Services/ClusterInfobaseCredentialsResolver.cs:109):
   при отсутствии совпадения логировать количество и список имён ИБ, возвращённых
   rac по каждому кластеру (новый ключ локализации, например
   `BatchOps.DbmsResolveClusterContentsFormat`: «Кластер {0}: баз в списке rac — {1}: {2}»).
   Чистый helper для формирования строки — покрыть юнит-тестом.
3. Fail-fast: если база клиент-серверная, сохранённого профиля СУБД нет, резолвер
   вернул null — не запускать ibcmd, а сразу зафиксировать статус «ошибка» с
   существующим понятным текстом [`BatchOps.NeedDbmsProfileFormat`](Workspace1C/Localization/Languages/ru.json:1011)
   (и новой строкой журнала с той же причиной). Результат прежний (база не
   выгружается), но причина видна сразу и операция не тратит время на ibcmd.
4. Локализация: новые ключи в [`ru.json`](Workspace1C/Localization/Languages/ru.json) и `en.json`.

### Риски
- Fail-fast меняет поведение (раньше ibcmd запускался «наудачу»): результат для
  пользователя всё равно ошибка, но с понятным текстом.
- Само сопоставление имён rac пока не меняем — сначала диагностика (п.2) даст
  фактический список имён; при подтверждении расхождения имён — точечный фикс в
  следующей версии.

### Критерии проверки
1. Массовая выгрузка серверной базы без профиля СУБД: в журнале окна — понятная
   причина (не пустое «завершилась ошибкой»).
2. При доступном rac: в журнале виден список имён ИБ кластера — по нему можно
   судить, почему база «не найдена».
3. Выгрузка серверной базы с заполненным профилем СУБД — проходит (регрессия нет).
4. Файловая база — без изменений.

## 3. Issue #89 — Скачивание EXE на Linux (критический крах старта)

### Суть (по последнему комментарию 7OH, 2026-11-01 11:45)
- Скачивание Linux-ассета починено в 1.0.1.9–1.0.1.11 (лог 7OH подтверждает:
  выбран корректный `Workspace1C-linux-x64`, 53304099 байт; остаточные жалобы на
  «в temp только .etag» от 1.0.1.9 закрыты диагностикой 1.0.1.11).
- **Актуальная проблема**: «Начиная с 1.0.1.12 вообще не запускается» —
  `System.FormatException: Invalid color string: '@WarningBrush'` в конструкторе
  `MainWindow` → приложение на Linux не стартует вовсе, обновиться невозможно.

### Причина (подтверждена кодом)
В [`MainWindow.Avalonia.Tree.cs:938`](Workspace1C/Views/MainWindow.Avalonia.Tree.cs:938)
и [`:944`](Workspace1C/Views/MainWindow.Avalonia.Tree.cs:944) в параметр `colorHex`
кнопок правой панели передаются **ключи кистей** `"@WarningBrush"` / `"@InfoBrush"`,
а [`CompactIconAndText`](Workspace1C/Views/MainWindow.Avalonia.Tree.cs:1250) (а также
строки 1267 и 1280–1281) вызывает `Color.Parse(colorHex)` напрямую → FormatException
при построении окна. Тот же паттерн в этом файле ещё в местах, куда могут приходить
`"@..."`-значения: строки 203–204 (правая панель), 759–760 (`BuildActionList` —
кортежи со `"@InfoBrush"`/`"@PurpleAccentBrush"`, строки 914–928), 1459 и 1474–1475
(`BadgeContent` — `"@WarningBrush"`/`"@PurpleAccentBrush"`, строки 956 и 973).

### Правки
Файл: [`Workspace1C/Views/MainWindow.Avalonia.Tree.cs`](Workspace1C/Views/MainWindow.Avalonia.Tree.cs)

1. Добавить приватный статический helper:
   `private static IBrush SpecBrush(string spec) => Themes.ThemeBrushes.FromSpec(spec);`
   — существующий [`ThemeBrushes.FromSpec`](Workspace1C/Themes/ThemeBrushes.Avalonia.cs:68)
   уже поддерживает обе формы спецификации: `"@КлючКисти"` и `"#RRGGBB"`.
2. Заменить `new SolidColorBrush(Color.Parse(colorHex))` на `SpecBrush(colorHex)`
   во всех перечисленных местах (203, 759, 1250, 1267, 1281, 1459, 1474) —
   семантика прежняя (у автора разметки это и были кисти темы).
3. Юнит-тест: чистый вызов `ThemeBrushes.FromSpec("@WarningBrush")` не бросает
   исключений и возвращает кисть (тест в `Workspace1C.Tests`, файл вида
   `ThemeBrushesFromSpecTests.cs`; проверить, что тест не требует UI-потока —
   `FromSpec` чистый, при необходимости разрешить ресурс через `Application.Current`
   guard/`#if` как в существующих тестах темы).

### Риски
- Затрагивается только цвет значков/подписей правой панели и бейджей; `FromSpec`
  возвращает именно те кисти темы, которые подразумевались вызовами.
- Обязательно проверить **Windows-сборку** после фикса: эти же пути исполняются
  и на Windows (там, вероятно, `Color.Parse` тоже падал бы — если Windows
  работал, значит ветки не выполнялись на Windows; после замены поведение
  Windows может визуально измениться на корректное «цвет темы»).

### Критерии проверки
1. Приложение стартует на Linux (сборка 1.0.1.17), правая панель отрисовывается.
2. Автообновление с Linux с предыдущей версии на 1.0.1.17 проходит (проверит 7OH).
3. Windows: главное окно, правая панель, бейджи — без визуальных регрессий.
4. Юнит-тест `FromSpec` зелёный.

## 5. Issue #79 — «Развернуть тестовую копию»

### Суть (по последнему комментарию 7OH, 2026-11-01 11:55)
Сценарий: серверная база, в списке сервера одна ИБ, в MS SQL одна БД; «Та же
ошибка — целевая база не найдена, хотя галочки про создание стоят» + скрин
«целевая база отсутствует». История: это развитие недоумения от 2026-10-31
(«А как она может быть найдена и для чего? Мы же в неё копию делаем») —
в 1.0.1.14 формулировки правились, в 1.0.1.15 был комментарий-объяснение.

### Предполагаемая причина
По совокупности скринов поведение мастера, скорее всего, **корректное**: предпросмотр
сообщает «тестовой базы ещё нет — будет создана новая»
([`TestDeploy.ActionCreate`](Workspace1C/Localization/Languages/ru.json:4218),
[`TestDeploy.PreviewUpdateFormat`](Workspace1C/Localization/Languages/ru.json:4215)),
но формулировка «ещё нет / не найдена» читается пользователем как **ошибка**, хотя
это штатный сценарий (галочка «Создавать базу данных на сервере СУБД» относится к
физической БД, а не к поиску записи в списке). Реальный сбой шага «Создание
тестовой базы»/«Загрузка» при этом не исключён — по логу на скрине однозначно
определить нельзя.

### Правки
1. Локализация (только текст, поведение не меняется):
   - [`ru.json`](Workspace1C/Localization/Languages/ru.json:4218) + `en.json`:
     `TestDeploy.ActionCreate` → позитивная форма без «нет/не найдена», например
     «Тестовая база будет создана с нуля; в списке баз её пока нет — это штатно».
   - `TestDeploy.PreviewUpdateFormat`/`TestDeploy.ActionUpdate` — проверить
     однозначность («уже есть в списке баз — данные будут заменены»).
   - `TestDeploy.PreviewSummaryFormat` — добавить явное «штатно/ошибки нет».
2. Проверить, что при сбое шага Create текст ошибки `CreateInfoBase` из
   [`TestDeployService.CreateTarget`](Workspace1C/Services/TestDeployService.cs:203)
   попадает в журнал мастера целиком (сейчас — попадает через
   `Fail(T("TestDeploy.Step.Create"), createError)`; убедиться, что окно не
   обрезает длинные ошибки платформы).

### Отметить: требуется уточнение пользователя
Если после 1.0.1.17 7OH сообщит, что развёртывание **реально не выполняется**
(а не смущает формулировка) — запросить полный текст журнала мастера
(шаг «Создание тестовой базы»: код возврата и stderr CREATEINFOBASE уже
возвращаются в `error`). Без этого текста точный код-фикс невозможен.

### Риски
- Минимальные: только строки локализации. Регрессия поведения исключена.

### Критерии проверки
1. Открыть мастер для серверной базы, у которой тестовой копии ещё нет: сводка
   предпросмотра читается как план действий, а не как ошибка.
