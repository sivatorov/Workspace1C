## 2. Issue #65 «Новинки программы — попытка номер 3»

### 2.1. Диагноз по коду (корень бага)
- [`UtilitiesMenuResolver.EnsureNewItemsGroup`](Workspace1C/Services/UtilitiesMenuResolver.cs:62): видимость группы «Новинки программы» вычисляется так:
  - `newItems = CollectNewItems(layout)` — пункты каталога с `IsNew`, **отсутствующие ВО ВСЕЙ компоновке** (по `CollectItemIds(layout.Root)`, строки 38–39);
  - если `newItems.Count == 0` → группе ставится `Visible = false` (строки 67–74), даже если **в самой группе ещё есть пункты**.
- Сценарий 7OH: в подменю 9 новых пунктов → пользователь переносит **один** в свою папку → теперь ВСЕ 9 пунктов «присутствуют» в компоновке (8 в группе `NewItems` + 1 в папке) → `CollectNewItems` возвращает пусто → группа скрывается, хотя в ней 8 пунктов. Точно такой же дефект в контекстном меню: [`ContextMenuResolver.EnsureNewItemsGroup`](Workspace1C/Services/ContextMenuResolver.cs:84) (тот же алгоритм).
- Замечание 7OH верно: «невидимо только в одном случае — когда там нет пунктов», но текущий код прячет группу по другому критерию.

### 2.2. Архитектура фикса (чистая логика, обе платформы)
Поменять алгоритм `EnsureNewItemsGroup` (аналогично — в `ContextMenuResolver`):
1. Видимость группы определяется **наличием пунктов в самой группе** (после добавления), а не пустотой «неразмещённых новинок по всей компоновке»:
   - если в каталоге есть неразмещённые `IsNew`-пункты — добавить их в группу (текущая ветка);
   - группа скрывается (`Visible = false`) **только если в ней не осталось ни одного пункта**;
   - если группа есть и не пуста — `Visible = true` **безусловно** (даже когда все новинки каталога уже размещены где-либо).
2. Критерий добавления в группу: пункт `IsNew`, которого нет **ни в группе, ни в остальной компоновке** (чтобы пункт, перенесённый пользователем в папку, не дублировался в «Новинках»).
3. При создании группы с нуля — прежняя логика (все неразмещённые новинки, `Visible = true`).
4. Применить тот же фикс в [`ContextMenuResolver.EnsureNewItemsGroup`](Workspace1C/Services/ContextMenuResolver.cs:84) — баг одинаковый (в плане: сделать отдельным пунктом; допускается в той же Code-задаче).

## 3. Issue #64 «Команды телеги»

### 3.1. Диагноз по коду
- [`TelegramBotCommandService.ParseUpdates`](Workspace1C/Services/TelegramBotCommandService.cs:158) берёт из message только `chat.id` (строки 176–180) и **не извлекает `message_thread_id`**. Сообщение из темы приходит с `chat.id` канала (например `-100…`) + `message_thread_id`.
- [`TelegramBotCommandService.AllowedChats`](Workspace1C/Services/TelegramBotCommandService.cs:122) возвращает **сырые строки** настроек: `AllowedChatIds` и `TelegramChatId` без нормализации (`t.me/c/…` → `-100…`, число → число). Сравнение `allowed.Contains(command.ChatId)` (строка 99) — строковое, без числового сравнения.
- В проекте уже есть готовый паттерн нормализации/сравнения: [`TelegramNotificationChannel.ParseChatTarget`](Workspace1C/Services/TelegramNotificationChannel.cs:80) (в т.ч. разбор `t.me/c/<id>/<thread>`) и [`SameChatId`](Workspace1C/Services/TelegramNotificationChannel.cs:135); `TelegramConfirmationService` (строки 165–166) уже использует `SameChatId`. `TelegramBotApiClient.SendAsync` уже поддерживает `message_thread_id` (строки 62–63).
- Итог: команда из темы настроенного чата игнорируется («команда из неразрешённого чата …проигнорирована»), т.к. значения не нормализуются и thread не учитывается.

### 3.2. Архитектура фикса (чистая логика + парсер, обе платформы)
1. `TelegramCommand` record ([`TelegramBotCommandService.cs`](Workspace1C/Services/TelegramBotCommandService.cs:27)) расширить: `long UpdateId, string ChatId, string? MessageThreadId, string Text`.
2. `ParseUpdates` — извлекать `message_thread_id` (и при желании `is_topic_message`) и класть в record.
3. Новая чистая функция разрешения вместо прямого `allowed.Contains`:
   - `public static bool IsAllowedChat(TelegramBotSettings settings, string? notificationChatId, string chatId, string? threadId)`:
     - собрать кандидатов: значения `AllowedChatIds` (сплит по `,; `) + при пустом списке — `notificationChatId`;
     - каждый кандидат нормализовать через `TelegramNotificationChannel.ParseChatTarget` → `(chatId0, threadId0?)`;
     - разрешено, если существует кандидат с `SameChatId(chatId0, chatId)` и (`threadId0 is null` **или** `threadId0 == threadId`) — настройка с темой разрешает только эту тему; без темы — чат целиком (основной + любые темы);
   - `AllowedChats(...)` оставить (обратная совместимость с тестами/внешними вызовами) или заменить — на усмотрение исполнителя, но основной путь — новая функция.
4. `LoopAsync` — использовать `IsAllowedChat(settings, channel.TelegramChatId, command.ChatId, command.MessageThreadId)` (строки 93–103) и передавать `command.MessageThreadId` в `SendAsync` (ответ — в ту же тему).
5. Локализация ru/en: подсказка в окне бота (ключ `Bot.AllowedChatsHint`) — можно указывать ссылку `t.me/c/<id>/<thread>` для приёма команд из конкретной темы.
