## Issue #114 «Линукс — статус панель» (по описанию, без комментариев)

### Текущее состояние (по коду)

- Строку состояния Avalonia строит `BuildStatusBar()` в
  [`Workspace1C/Views/MainWindow.Avalonia.cs:2163`]:
  - `_statusInfo` — `TextBlock` (строки 2172–2194), `TextTrimming=CharacterEllipsis`;
  - tooltip: `_statusInfo.Bind(ToolTip.TipProperty, new Binding("StatusBarInfo"))` (строка 2178) — **строка целиком, без переноса и без wrapping**;
  - ContextMenu: создаётся в 2181–2185 (`ModernContextMenu`), пункты «Копировать ИД» (`Main.StatusIdCopy`) и «Копировать путь» (`Main.CopyPath`), `DoubleTapped` копирует ИД. **Placement/PlacementTarget не заданы** — на X11 Avalonia позиционирует pointer-based popup неровно (известная проблема popup-placement на некоторых WM/композиторах), отсюда «меню совсем не там».
- Текст статуса собирает `ComposeStatusInfo` в
  [`Workspace1C/ViewModels/MainViewModel.Avalonia.Display.cs:991`]: части соединяются `"  ·  "`, ИД добавляется последним (строки 1016–1017: `parts.Add($"ID {ib.Id}")`).
- В репозитории уже есть отработанный механизм зажима popup-позиции:
  [`PopupBoundsMath.cs`](Workspace1C/Services/PopupBoundsMath.cs) + `PlacementMode.Custom` — используется панелью выбора окон у индикатора загрузок (`MainWindow.Avalonia.cs:2328–2364`, issue #282/#359). Его переиспользуем.

### Изменения

1. **Перенос строки перед ИД в tooltip (не в самой панели).**
   - В `MainViewModel.Avalonia.Display.cs` добавить Avalonia-only свойство `StatusBarInfoTip` (рядом с `StatusBarInfo`, оба уведомляют `OnPropertyChanged`): та же строка, но перед частью `ID {…}` вставляется `\n`. Реализация: собрать те же `parts` и соединить последнюю (ИД) переносом, либо пост-обработка: `StatusBarInfoTip = StatusBarInfo.Replace("  ·  ID ", "\nID ")` — выбрать вариант при реализации, сохранив единый источник (`ComposeStatusInfo`).
   - В `MainWindow.Avalonia.cs` вместо привязки `ToolTip.Tip` к строке — привязка к `StatusBarInfoTip` c **кастомным содержимым tooltip**: `ToolTip` с `TextBlock { TextWrapping = Wrap, MaxWidth ≈ 480 }`, чтобы длинный путь/ИД переносились и не усекались экраном.
   - `StatusBarInfo` (одна строка в панели) — **не менять** (перенос в ней сломал бы нижнюю панель).
2. **Позиционирование tooltip.** Задать явное размещение: `ToolTip.Placement = PlacementMode.Top` с `PlacementTarget = _statusInfo` (панель внизу окна — подсказка должна открываться ВВЕРХ, а не «где-то»): свойство задать на `ToolTip`-объекте, который привязывается как контент (`ToolTipService.SetTip` c готовым `ToolTip`).
3. **Позиционирование ContextMenu.**
   - `statusMenu.PlacementTarget = _statusInfo`; `statusMenu.Placement = PlacementMode.Top` (или `PlacementMode.Custom` с `PopupBoundsMath` по образцу `ShowDownloadsPicker`, если якорное размещение на X11 всё ещё скачет). Якорь — сам элемент строки состояния, а не курсор: pointer-based placement и есть источник «меню не там».
   - Проверить `VerticalOffset/HorizontalOffset` не заданы нигде глобально (`Themes/Controls.axaml`, `ControlDefaults.axaml` — стиль `ModernContextMenu`), при необходимости добавить offset только для этого меню.
4. **Прогнать паритет с WPF**: WPF-версия (`MainWindow.xaml:2288–2292`) — контекстное меню и tooltip строки состояния; убедиться, что поведение совпадает (там TooltipService показывает строку целиком).

### Тесты (`Workspace1C.Tests`, новый файл `Issue114StatusBarTooltipTests.cs`)

Код `MainViewModel.Avalonia.*`/`MainWindow.Avalonia.cs` компилируется только в Linux-конфигурации (`#if LINUX`), поэтому тесты — по образцу source-scan из `Issue79ScheduledJobsResilienceTests.cs` (`ReadProjectFile`):
- строка `ComposeStatusInfo` содержит формирование ИД и новая логика `StatusBarInfoTip` вставляет `\n` перед `ID`;
- в `MainWindow.Avalonia.cs` tooltip привязан к `StatusBarInfoTip`, `TextWrapping = Wrap` задан;
- `statusMenu.Placement`/`PlacementTarget` установлены (страж против регрессии «меню не там»).

### Риски

- Avalonia 11 на разных WM позиционирует popup по-разному: якорное размещение (`PlacementTarget`) стабильно на X11/Wayland, но точный вид проверить только на живой Linux-машине у 7OH (скрин в issue). Риск: останется смещение на экзотических WM — в этом случае следующий шаг: `PlacementMode.Custom` + `PopupBoundsMath` (механизм уже есть).
- Перенос перед ИД: пользователь просил «перенос перед началом ИД» — реализуем именно в tooltip, чтобы не ломать однострочную панель.

## Issue #107 «Неисправленные огрехи в тёмной теме» (комментарий 7OH от 2026-11-07)

### Текущее состояние (по коду)

- [`App.axaml:6`] — `RequestedThemeVariant="Default"`; подключены `FluentTheme` и `LightTheme.axaml`.
- Старт (`App.axaml.cs:293–318`): читаются настройки → `ThemeManager.ApplyFullTheme(fullTheme)` (задаёт `RequestedThemeVariant` и палитру схемы) → `ThemeFeatureMap.ResolveDarkVariant(settings.Theme) is bool darkVariant` → `ApplyTheme(darkVariant)` → `ApplyScheme(mergedScheme)` → строится и показывается `MainWindow`. Тот же порядок в `LoginWindow.Avalonia.cs:71–73` и `App.xaml.cs` (WPF).
- [`ThemeManager.Avalonia.cs`] — `ApplyTheme(bool)` (87–111) ставит `RequestedThemeVariant`, `ApplyFullTheme(string?)` (173–186) резолвит тему через `ThemeFeatureMap.Resolve(id)`; `ApplyColors(app, scheme, dark)` (535+) накладывает палитру схемы как ресурсы приложения. **Кисти содержимого Fluent-контролов (например foreground кнопок) палитрой не переопределяются** — они берутся из FluentTheme по `ThemeVariant`.
- Симптом на скрине 7OH: светлая (яркая) подложка окна из собственной палитры, но **белый текст на кнопках** — типичный вид, когда содержимое контролов резолвится по варианту `Dark` (или по «не переопределённым» Fluent-цветам), а фон окна/карточек — из светлой палитры приложения. Т.е. вариант темы и палитра рассинхронизированы: окна/панели красятся ресурсами `LightTheme.axaml`, а Fluent-контролы остаются в тёмном варианте.

### Изменения (последовательность: сначала диагностика, потом фикс)

1. **Диагностика (шаг реализации №1):** в лог старта (`LogStartupStage`) добавить запись фактического `Application.Current.RequestedThemeVariant`, `ThemeManager.CurrentTheme` и имени `settings.NormalizeThemeSelection()` на Linux. По новому ZIP/логу от 7OH (или локальному прогону) подтвердить: приходит ли на Linux `ThemeVariant.Dark` при дефолтных настройках, и откуда (сохранившийся `Theme="Dark"` в настройках / `NormalizeThemeSelection()`/`ThemeFeatureMap.Resolve(null)` / системная тема X11 через `PlatformSettings`).
2. **Фикс А — никогда не оставлять `RequestedThemeVariant="Default"` на Linux.** Даже при дефолтных настройках явно ставить `ThemeVariant.Light` (дефолт приложения — светлая тема `ColorScheme.CreateLight()`):
   - в `ThemeManager.Avalonia.cs` гарантировать, что `ApplyFullTheme`/`ApplyTheme` всегда ставят **явный** вариант (сейчас ставят — проверить ветку, где `ResolveDarkVariant` вернул `false`/null, и вариант остаётся `Default` из `App.axaml`);
   - в `App.axaml` можно оставить `Default`, но в `OnFrameworkInitializationCompleted` вариант задаётся **до построения любого окна** (сейчас так и есть — проверить, что в ветке ошибки/раннего выхода вариант тоже задаётся).
3. **Фикс Б — палитра перекрывает Fluent-цвета кнопок.** В `ApplyColors` (или в палитрах `ColorScheme.CreateLight/CreateDark`) добавить переопределение ресурсов содержимого контролов, которые Fluent берёт по варианту (как минимум: `Button` foreground поверх `AccentBrush`-подобных ярких подложек и дефолтный foreground обычной кнопки). Это гарантирует читаемый текст при любом рассогласовании варианта/палитры (то же, что уже сделано для радио-кнопок в `ConfigDiffSetupWindow.Avalonia.cs:108–110` — там комментарий прямо про «FluentTheme может оставить тёмный текст»).
4. **Фикс В — уважать системную тему при отсутствии настройки (опционально).** Если по диагностике подтвердится, что на Linux `PlatformSettings.ThemeVariant` даёт Dark, а пользователь ни разу не выбирал тему — при «настройка не задана» синхронизировать вариант с системной темой (`app.PlatformSettings.ThemeVariant`), чтобы «тёмная система → тёмное приложение», а не рассинхрон. Фикс Б при этом остаётся страховкой.
5. Локализация не требуется (изменения без новых строк или с парой ключей ru/en, если появится подпись).

### Тесты

- Новый `Issue107LinuxDefaultThemeTests.cs` (source-scan + чистые функции):
  - страж: в `ThemeManager.Avalonia.cs` после `ApplyTheme`/`ApplyFullTheme` `RequestedThemeVariant` всегда Light/Dark (никогда не Default) — по тексту кода;
  - страж: `ApplyColors` переопределяет ключи foreground кнопок (перечень ключей фиксирован в тесте);
  - при наличии чистой функции «вариант по настройке/системе» — юнит-тесты на ветки (настройка задана светлая/тёмная/не задана + системная Light/Dark) — по образцу `FullThemeSelectionTests.cs`/`ThemeFeatureMapTests.cs`.

### Риски

- Изменение дефолта варианта при «настройка не задана» может изменить вид у части пользователей (было Dark-подобное дефолтное) — принять сознательно, упомянуть в CHANGELOG.

## Issue #79 «Развернуть тестовую копию» (комментарий 7OH от 2026-11-07T08:00:24Z)

### Текущее состояние (по коду)

Порядок шагов `DeployAsync` ([`TestDeployService.cs:59–293`]):
1. pre-валидация → 2. выгрузка .dt → 3. группа → 4. **создание/обнаружение целевой базы** (`CreateTarget`, строки 160–181) → 5. **RestoreIB** (183–203) → 6. **выключение регламентных заданий** (209–224, `DisableScheduledJobsAsync` 553–585: COM `ScheduledJobsService.SetAllAsync`, затем `EvaluateJobsStep` 609+ с `VerifyAsync` — повторное чтение и **подсчёт включённых заданий `state.Enabled`**) → 7. маркеры → 8. группа.

Инфраструктура кластерной блокировки уже есть и используется в других фичах:
- `RacInfobaseUpdateRequest.ScheduledJobsDeny` ([`RacModels.cs`](Workspace1C/Models/RacInfobaseUpdateRequest.cs)) и `RacClient.UpdateInfobaseAsync` (`--scheduled-jobs-deny=on`, [`RacClient.cs:712–713`]);
- образец «прочитать текущее состояние через infobase info → выставить deny → при необходимости вернуть» — [`BatchOpsPreparationService.cs:253–358`];
- образец «сначала блокировка, потом действие» — `ServerMonitorViewModel` (`BlockScheduledJobs`, строки ~1437–1481).

### Причины трёх претензий 7OH

1. **«Внутренняя ошибка» остаётся после v1.0.1.42** — COM-чтение свойств заданий сразу после RestoreIB падает на «прогреве» метаданных; per-job try/catch + verify не убирают сообщение, т.к. verify сам читает COM и тоже падает/считает. Корень — COM-шаг выполняется сразу после RestoreIB.
2. **«Почему задания выключаются ПОСЛЕ загрузки?»** — потому что сейчас так: шаг 6 после шага 5. Правильно (по предложению 7OH и по механике): кластерная галочка `scheduled-jobs-deny=on` ставится **сразу после создания/обнаружения целевой базы — ДО RestoreIB**. Тогда задания вообще не стартуют во время загрузки, и «прогрев» метаданных не ломает COM.
3. **«Откуда сообщение? Что мы пытаемся определить? Количество чего?»** — это `VerifyAsync`/`EvaluateJobsStep`: после сбоя операции мы повторно читаем все задания через COM и считаем, сколько осталось включёнными (`state.Enabled`), чтобы отличить ложную ошибку от реальной. Хрупкая логика — убираем/упрощаем.

### Изменения

1. **Новый шаг «блокировка регламентных заданий» ДО загрузки** (после шага 4 «создание/обнаружение целевой базы», перед RestoreIB), только для клиент-серверных целевых баз:
   - резолв параметров кластера для целевой базы: адрес кластера/ИД инфобазы — по образцу `BatchOpsPreparationService` (rac `infobase info` по имени базы, с кредами ИБ из формы/сценария, как в v1.0.1.26+);
   - `rac infobase update --scheduled-jobs-deny=on` через `RacClient.UpdateInfobaseAsync`;
   - инъекция rac: `TestDeployService` получает `IRacClient` (DI) + optional test-override (по образцу `ScheduledJobsService.VerifyOverride`) для юнит-тестов;
   - результат: успех → в `result.Log` шаг `TestDeploy.Step.DenyJobs` + факт «галочка установлена»; сбой rac → **warning в журнал, НЕ ошибка**: развёртывание продолжается, COM-путь (п.3 ниже) остаётся как fallback;
   - новая платформа-поведение: на **Linux** этот шаг тоже работает (rac доступен) — сейчас там шаг заданий просто логирует `TestDeploy.JobsLinuxSkipped`; блокировка ДО загрузки закрывает и Linux-кейс.
2. **Шаг 6 (после RestoreIB) упростить:**
   - если кластерная блокировка на шаге до загрузки установлена успешно — **COM-шаг пропускается** (галочка уже держит задания выключенными; это и есть запрошенная логика), в журнал пишется соответствующая строка;
   - если rac недоступен/файловая база/сбой rac — сохраняется существующий устойчивый COM-поток v1.0.1.42 (per-job try/catch), но **verify-подсчёт упрощается**: `EvaluateJobsStep` больше не интерпретирует «все задания выключены фактически» как отдельную ветку с подсчётом; при сбое COM — warning с расшифровкой (текст уже есть: `ExplainComInternalError`), без ошибок, развёртывание считается успешным. Ответ на вопрос 7OH «что мы считаем?» больше не нужен пользователю — подсчёт удалён из UX.
   - `DisableScheduledJobsAsync`/`EvaluateJobsStep`/`JobsStepOutcome` чистятся соответственно (оценить, остаётся ли `EvaluateJobsStep` вообще — если COM-ветка сводится к «warning всегда», функция упрощается или удаляется вместе с тестами-стражами).
3. **Обработка ошибки**: любые сбои шага блокировки/заданий — `result.Warnings` + строки журнала; `result.Success` не роняется (паритет с v1.0.1.40+); «Внутренняя ошибка» COM при пропущенном COM-шаге возникать больше не должна.
4. **Локализация** (`Localization` ru/en): новые ключи `TestDeploy.Step.DenyJobs`, `TestDeploy.JobsDenySet`, `TestDeploy.JobsDenyFailed` (warning), `TestDeploy.JobsSkippedDenyApplied`; удалить/пометить устаревшими `TestDeploy.JobsDisabledVerified`, `TestDeploy.JobsVerifyRemaining` (если verify убран).
5. **Порядок шагов в `DescribeSteps`/preview мастера** (`TestDeployPlanner.DescribeSteps`) — вставить шаг блокировки между «Создание/Обновление» и «Загрузка».
