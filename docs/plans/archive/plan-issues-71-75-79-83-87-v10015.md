## Issue #71 — Запоминание размеров окон «Настройки» и «Настройка информационной базы»

### Что требуется (по последнему комментарию @RizvanShikhammatov)
«Да, теперь работает. Но нельзя ли запоминать размеры этого окна? И в следующий раз открывать с последними размерами?»

Запоминать **размеры** (не позицию — окна открываются по центру владельца, `CenterOwner`/центр экрана). Минимумы 960×720 / 760×780 и зажим минимума (уже сделан в 1.0.1.3/1.0.1.4) сохраняются: восстановленный размер клампится к `MinWidth/MinHeight`.

### Переиспользуемые механизмы
- Главное окно уже сохраняет размер/позицию: `AppSettings.WindowWidth/Height/Left/Top` ([`AppSettings.cs`](Workspace1C/Models/AppSettings.cs:470)) + `MainViewModel.SaveWindowLayout` (WPF: [`MainViewModel.Launch.cs`](Workspace1C/ViewModels/MainViewModel.Launch.cs:668), Avalonia: [`MainViewModel.Avalonia.cs`](Workspace1C/ViewModels/MainViewModel.Avalonia.cs:344)) + зажим к минимуму при восстановлении ([`MainWindow.Avalonia.cs`](Workspace1C/Views/MainWindow.Avalonia.cs:2529)).
- `WindowOwnerResolver`, провайдеры настроек через `IInfobaseRepository.LoadSettings()`/`SaveSettings(...)` (образец: [`App.xaml.cs`](Workspace1C/App.xaml.cs:225)).

### Изменения

**1. `Workspace1C/Models/AppSettings.cs`** — добавить 4 свойства со значением 0 по умолчанию (0 = «не задано»):
- `double SettingsWindowWidth`, `double SettingsWindowHeight`;
- `double ConnectionSettingsWindowWidth`, `double ConnectionSettingsWindowHeight`.

**2. Общий хелпер (новый файл) `Workspace1C/Services/WindowSizeStore.cs`** — чистые функции, обе платформы, покрыты тестами:
- `double ApplyMin(double saved, double min)` → `saved <= 0 ? 0 : Math.Max(saved, min)` (0 — «не восстанавливать», оставить стартовый);
- `bool IsValid(double v)` → `v > 0 && !double.IsNaN(v) && !double.IsInfinity(v)`.
- Методы чтения/записи размеров для окна «Настройки» и «Настройка информационной базы» (по типам окон, enum `StoredWindowKind { Settings, ConnectionSettings }`), работающие с `AppSettings`.

Если существуют более «стайл-истичный» способ доступа к настройкам в WPF-версии окна — использовать его (учесть, что окно также вызывается из мастера тестовой копии и `MainViewModel.Commands.cs`).

**6. Avalonia, `Workspace1C/Views/ConnectionSettingsWindow.Avalonia.cs`** — аналогично п.5 (конструктор [`строки 66-91`](Workspace1C/Views/ConnectionSettingsWindow.Avalonia.cs:66), зажим уже есть), чтение/запись через `IInfobaseRepository`.

### Риски
- Восстановление размера раньше `ShowDialog` — окно может «мигнуть»; минимизируется установкой размера в конструкторе (до показа).

- DPI: сохраняются логические единицы WPF/дип-юниты Avalonia — аналогично тому, как уже сохраняется главное окно; отдельной обработки не требуется.

### Гипотеза, почему у пользователя не срабатывает (проверить на шаге диагностики)
1. Клик/перетаскивание обрабатывает штатный механизм DataGrid (Thumb `PART_RightHeaderGripper`), а наш `PreviewMouseLeftButtonDown` не вызывает `StartColumnDrag` (не тот `OriginalSource`, клик не в зоне 24 px, `FindAncestor` не находит заголовок, обработчик потерян из-за пересоздания заголовков на вкладках).
2. `StartColumnDrag` вызывается, но штатный Thumb всё равно успевает захватить мышь (захват идёт не через tunnel в тот же момент), и после нашего `CaptureMouse`/обновления ширин штатный механизм перезаписывает ширины — пользователь видит «ужимание двух колонок».

## Issue #83 — Утилита ring не находится во вкладке «Лицензии»

### Что требуется (последний комментарий @7OH)
«Что-то не легчает. Ошибка всё та же» — лог: `ring (PATH) — утилита лицензий недоступна: ring: An error occurred trying to start process 'ring' with working directory … Не удается найти указанный файл`.

### Первопричина (гипотеза, подтверждённая кодом)
`where.exe ring` может находить утилиту, которую `Process.Start` (CreateProcess, `UseShellExecute=false`) не может запустить без расширения по `PATHEXT` — например, `ring.cmd`/`ring.bat`. В ручной командной строке (`cmd.exe`) это работает, потому что `cmd` применяет `PATHEXT`; наш `ProcessRunner` — нет. Поэтому доступность подтверждается (`ringInPath != null`), кандидат `ring (PATH)` добавляется, а реальный запуск даёт `Не удается найти указанный файл`.

### Решение
Использовать полный путь из `where.exe ring` (Windows) / `which ring` (Linux) и запускать его в **том виде, в котором его может выполнить ОС**:
- `.exe` / `.com` / без расширения (Linux) — прямой запуск полного пути;
- `.cmd` / `.bat` — запуск через `cmd.exe /c "<путь>" license list` (Windows) — точно повторяет поведение командной строки пользователя;
- если `where`/`which` не дали результата — запасной probe `ring --version` выполняется так же (через `cmd.exe /c` на Windows); если сработал — вызвать `ring license list` через `cmd.exe /c ring license list`.

### Изменения (только [`Workspace1C/Services/RingLicenseService.cs`](Workspace1C/Services/RingLicenseService.cs) + тесты)
1. Новая internal-функция разложения пути на «исполняемый вызов»:
   `internal static (string Command, string[] Arguments) ToLaunchCommand(string ringPath, params string[] toolArgs)`:
   - расширение `.cmd`/`.bat` (Windows) → `("cmd.exe", new[] { "/c", ringPath }.Concat(toolArgs))`;
   - иначе → `(ringPath, toolArgs)`.
2. `FindRingInPathAsync` возвращает `string?` (путь из `where`/`which`; для ветки `--version` — маркер `"ring"`), НО добавить возврат типа «команда-обёртка» — изменить на `internal static async Task<(string? Path, bool NeedsShellAsync?)>` либо оставить `string?` и помещать в кандидаты уже разложенный вызов (рекомендуется второй вариант — меньше менять интерфейс):
   - в `GetInstalledLicensesAsync`: `var ringInPath = await FindRingInPathAsync(...)`; если `ringInPath` не null → `resolveLaunch = ToLaunchCommand(ringInPath, "license", "list")` и добавить его как единственный кандидат «ring (PATH)» (вместо константного ("ring", …)).
   - `CommandCandidates(bool includePathRing, string? ringPath = null)` — перегрузка: при `ringPath` присутствии строит вызов по правилу п.1, иначе сохраняет прежние кандидаты (bin платформы/licensetool).
3. `BuildUnavailableMessage()` — текст подсказки дополнить: «ring может быть установлен как .exe в каталоге bin платформы либо добавлен в PATH (в т.ч. как командный файл .cmd/.bat); проверка выполняется так же, как в командной строке».
4. Логика проб `where.exe ring`/`which ring` и INFO-логирования — сохраняется как есть.

Внимание: тесты [`Issue83LicenseTabTests.cs`](Workspace1C.Tests/Issue83LicenseTabTests.cs) содержат страж `RingCandidate_IsInvokedAsIs_AndSkippedWhenPathProbeFailed` (ожидает `Command == "ring"`) — **обновить** под новый контракт (см. ниже).

### Тесты (обновить/добавить в `Issue83LicenseTabTests.cs`)
- `ToLaunchCommand_Exe_IsInvokedDirectly`: `ring.exe` → `("C:\\bin\\ring.exe", ["license","list"])`.
- `ToLaunchCommand_CmdFile_IsInvokedViaCmdExe`: `ring.cmd` → `("cmd.exe", ["/c", "C:\\bin\\ring.cmd", "license","list"])`.
- `ToLaunchCommand_NativeLinux_IsInvokedDirectly`: `/usr/bin/ring` → `("/usr/bin/ring", ["license","list"])`.
- `RingCandidate_FromWherePath_UsesResolvedCommand`: `CommandCandidates(includePathRing: true, ringPath: "C:\\bin\\ring.exe")` содержит вызов с полным путём.
- Существующие тесты `RingUnavailable*`, порядок вкладок, `FirstNonEmptyLine` — сохранить.

### Риски
- Кодировка вывода `ring` под `cmd /c` может быть OEM (866) — `ProcessRunner` качает UTF-8. Парсер лицензий опирается на hex-серийники (регистронезависимые) и ключевые слова — искажение кириллицы некритично для распознавания серийных номеров; при желании добавить декодирование CP866 для `.cmd`-ветки (опционально).
- Пользователь может иметь настоящий `.exe` и проблему в другом (например, PATH у процесса приложения отличается от PATH пользователя после его изменения «на лету»); в этом случае `where.exe` тоже не найдёт/найдёт неправильно — план покрывает только корректный запуск найденного пути. Вариант с `cmd.exe /c ring …` (без пути) в запасном probe частично страхует.
- Не трогать Linux-ветку licensetool (работает напрямую по полному пути).

## Issue #87 — Загрузка расширения с «общей авторизацией приложения»

### Что требуется (последний комментарий @aepkugesi)
Если логин/пароль заданы в самой базе — расширение грузится; если заданы в настройках приложения «общая авторизация» — конфигуратор падает: `The infobase user is not authenticated`.

### Первопричина (подтверждена кодом)
[`DesignerCommandRunner.RunAsync`](Workspace1C/Services/DesignerCommandRunner.cs:71) строит авторизацию через `OneCLauncher.BuildAuthArgument(infobase)` ([`OneCLauncher.Arguments.Shared.cs`](Workspace1C/Services/OneCLauncher.Arguments.Shared.cs:423)), который вызывает `InfobaseAuthResolver.Resolve(infobase, Configurator, out …, out …, out …)` с однопараметровой перегрузкой → `commonAuth = null`.
